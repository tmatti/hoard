The 13 options in GitHub's license picker

When you click Add file → Create new file → LICENSE (or "Choose a license"), GitHub offers licenses curated by choosealicense.com. They fall into three families. The right pick is a trade-off between adoption (how freely others can use your code) and protection (how much you force back into the open).

The core trade-off
Permissive

Maximize adoption

Let anyone do almost anything — including building closed, commercial products — as long as they keep your copyright notice. Best for libraries, frameworks, and wide reach. MIT, Apache-2.0, BSD, Boost.

Copyleft

Keep it open

Anyone can use it, but derivatives must stay open under the same/compatible license and ship source. Scope ranges from a single file to the whole work to network use. MPL, LGPL, EPL, GPL, AGPL.

Public domain

No strings at all

Waive essentially all rights. No attribution required. Maximum freedom, but weaker legal footing and no patent grant. Unlicense, CC0.

Rule of thumb: Want the widest possible use with least friction? MIT. Same, but you also want explicit patent protection? Apache-2.0. Want improvements to come back to you? MPL-2.0 (file-level) or GPL (whole-app). Running a network service and want SaaS users to get the source? AGPL-3.0.
⚠ Educational summary, not legal advice. Authoritative text lives at choosealicense.com and the SPDX license list. When in doubt, consult a lawyer.

License families: from permissive to network-copyleft

The single most useful axis is how much obligation a license imposes on people who build on your code. Left = none; right = strong, viral, network-spanning. Picking a family first narrows 13 options to 2–3.

← fewer obligations · max adoptionmore obligations · max protection →
Public domain
All rights waived. No attribution, no conditions.
  • Unlicense
  • CC0-1.0
Permissive
Do anything, just keep the notice. Closed forks allowed.
  • MIT
  • BSD-2 / BSD-3
  • Boost (BSL-1.0)
  • Apache-2.0
Weak copyleft
Only changed files / the library itself stay open.
  • MPL-2.0 (file)
  • EPL-2.0 (file)
  • LGPL-3.0 (library)
Strong copyleft
Whole derivative work must be open under GPL.
  • GPL-2.0
  • GPL-3.0
Network copyleft
Even SaaS users must be offered the source.
  • AGPL-3.0
What "copyleft scope" actually means

File-level (MPL, EPL)

Changes to licensed files must be shared, but you can combine them with proprietary files in a larger work. Friendliest copyleft for mixed/commercial codebases.

Library boundary (LGPL)

Link the library (especially dynamically) into a proprietary app freely; modifications to the library stay LGPL, and users must be able to swap in their own build.

Whole-work (GPL)

Any program that incorporates GPL code becomes a derivative — the entire thing must be distributed under the GPL with source. This is the "viral" reputation.

Network (AGPL)

Closes the "SaaS loophole." If users interact with modified code over a network, that counts as distribution — you must offer them the source too.

Compatibility gotcha: Apache-2.0 is not compatible with GPL-2.0 (its patent terms clash) but is compatible with GPL-3.0. GPL-2.0-only code can't be combined with GPL-3.0 code unless it's "v2 or later." Mixing licenses is where most real-world legal pain comes from.

Decision guide

Walk top to bottom. The first question that matches your priority usually points to one or two licenses.

Q1
Do you care what others do with derivatives?
No, max adoption→ permissive: MIT / Apache-2.0
Yes, keep it open→ copyleft (go to Q3)
Don't care at all→ public domain: Unlicense / CC0
Q2
(Permissive) Do you need explicit patent protection?
Yes→ Apache-2.0 (patent grant + retaliation clause)
No, keep it minimal→ MIT or BSD-3-Clause
C++ / no notice in binaries→ Boost (BSL-1.0)
Q3
(Copyleft) How wide should the obligation reach?
Just my files→ MPL-2.0 (or EPL-2.0 for Java/Eclipse)
Just my library→ LGPL-3.0 (proprietary apps can link)
The whole app→ GPL-3.0 (or GPL-2.0 for kernel-style)
Even network/SaaS use→ AGPL-3.0
Q4
Matching an existing ecosystem?
Rust / Node / Go→ MIT or Apache-2.0 (dual is common)
Linux kernel / coreutils→ GPL-2.0
Java / Eclipse→ EPL-2.0
Selling open-core SaaS→ AGPL-3.0 + CLA
Reality check: Many companies (famously Google) forbid using AGPL — and sometimes GPL — code internally. If your goal is for big companies to adopt your library, a permissive license removes that barrier entirely. Conversely, copyleft is leverage if you sell commercial exceptions (the "open-core" model).
⚠ Educational summary, not legal advice. Verify against choosealicense.com and SPDX, and talk to a lawyer for anything that matters commercially.
