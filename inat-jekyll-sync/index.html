Operations

Auto-post iNaturalist observations to a Jekyll blog

A scheduled GitHub Action pulls fresh observations from iNaturalist's public API, renders them into Markdown posts, validates with a full jekyll build, and pushes to main. Zero secrets, zero external dependencies, ~250 lines of Ruby.

Goal

Mirror your iNaturalist observations into a dedicated section of your Jekyll/GitHub Pages blog. Daily cadence. Hands-off after first-run backfill.

Architecture

Three moving parts, one repo.

Data flow

iNaturalist API
     │
     │  GET /v1/observations?user_login=...
     │  (anonymous, paginated 200/page via id_above)
     ▼
GitHub Action runner (Ubuntu)
     │
     │  ruby scripts/inat_sync.rb
     │      reads  _data/inat_published.yml
     │      writes _posts/*.md
     │      writes _data/inat_published.yml
     │
     │  bundle exec jekyll build --strict_front_matter
     │      (fail-stop gate)
     │
     │  git commit + push to main
     ▼
GitHub Pages build
     │
     ▼
Live site — /observations/ landing + tagged posts

State

  • _data/inat_published.yml — the only piece of stateful data. A sorted list of integer iNat observation IDs.
  • _posts/*.md — immutable artifacts once written.
  • No database, no S3, no API token, no rotating secrets.

Trust boundaries

  • iNat API is treated as untrusted input — script never evals or shells out with API data.
  • Default GITHUB_TOKEN is scoped to contents: write on this repo only.
  • No third-party Actions used beyond actions/checkout and ruby/setup-ruby, both first-party / well-audited.

iNaturalist API notes

Public REST API at https://api.inaturalist.org/v1/. Documented at api.inaturalist.org/v1/docs.

Request used

GET https://api.inaturalist.org/v1/observations
       ?user_login=<LOGIN>
       &per_page=200
       &order_by=id
       &order=asc
       &id_above=<LAST_ID>

Headers:
  User-Agent: jekyll-inat-sync/0.1 (+https://github.com/...)
  Accept:     application/json

Pagination

Keyset pagination via id_above: start with id_above=0, ask for ascending order, capture the max id from the returned page, repeat. More reliable than offset pagination for large result sets and idempotent across concurrent uploads.

Relevant response fields (per observation)

FieldUsed for
idManifest key + post anchor.
uri"View on iNaturalist" link.
observed_onBackfill grouping key; date line in post body.
place_guessLocation text (already fuzzy / privacy-respecting).
descriptionUser's narrative paragraph if present.
photos[].urlHero + gallery. Swap square for medium.
taxon.preferred_common_namePost heading; "Western Fence Lizard".
taxon.nameScientific name italic line.

Rate limits

  • ~100 requests/min, ~10,000/day (iNat's recommended-practices page).
  • Even 10k observations × (per_page 200) = ~50 requests. We're nowhere near the ceiling.
  • Script sleeps 0.7s between pages out of politeness; far below the limit.

Photo URL trick

The API returns photos[].url as the square (75×75) thumbnail. Swap the path segment to get other sizes: 

https://inaturalist-open-data.s3.amazonaws.com/photos/123/square.jpg
                                                          ^^^^^^
                                              swap to: small / medium / large / original

The sync script

scripts/inat_sync.rb — ~250 lines, Ruby stdlib only (net/http, json, yaml, erb).

Flow

  1. Parse CLI flags (--user, --dry-run, --backfill, --photo-size).
  2. Load manifest from _data/inat_published.yml.
  3. Fetch all observations via keyset pagination, sleeping 0.7s between pages.
  4. Filter out IDs in the manifest.
  5. Group: by observed_on if --backfill, else everything into today's group.
  6. Render one post per group via ERB.
  7. Append new IDs to the manifest and write it back.

Post filename pattern

_posts/YYYY-MM-DD-observations-<slug>-<hash>.md

  YYYY-MM-DD    The post's date (run-date in steady-state, observed_on in backfill)
  slug          Slugified common name of the hero observation
  hash          6-char SHA1 of sorted obs IDs — idempotency guard

The hash prevents accidental filename collisions when two runs on the same date produce different post contents (rare edge case — e.g., a backfill re-run after manually deleting a post).

GitHub Action workflow

.github/workflows/inat-sync.yml. Daily cron + workflow_dispatch with a backfill toggle. 

name: iNaturalist sync

on:
  schedule:
    - cron: "0 7 * * *"   # 07:00 UTC daily
  workflow_dispatch:
    inputs:
      backfill:
        type: boolean
        default: false

permissions:
  contents: write

concurrency:
  group: inat-sync
  cancel-in-progress: false

jobs:
  sync:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ruby/setup-ruby@v1
        with: { ruby-version: "3.3", bundler-cache: true }

      - name: Run sync
        env:
          INAT_USER: ${{ vars.INAT_USER }}
          BACKFILL_FLAG: ${{ inputs.backfill && '--backfill' || '' }}
        run: ruby scripts/inat_sync.rb --user "$INAT_USER" $BACKFILL_FLAG

      - name: Build Jekyll site (gate)
        run: bundle exec jekyll build --strict_front_matter

      - name: Commit and push
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add _posts/ _data/inat_published.yml
          git diff --quiet --staged || git commit -m "Sync iNaturalist $(date -u +%F)"
          git push

Why a build gate?

If the script ever emits malformed frontmatter or a busted Liquid tag, the Jekyll build fails — and we want that failure to happen in CI, not on the live gh-pages build (which only sends you an email and serves a stale site). --strict_front_matter turns frontmatter parse errors into build failures.

Concurrency

concurrency.group: inat-sync means only one run executes at a time. If a manual backfill is running and the daily cron fires, the cron waits. Prevents two runs racing on the same manifest.

Landing page

observations.html at site root, permalinked to /observations/. Iterates site.tags.inaturalist in reverse chronological order and renders the hero_photo from each post's frontmatter as a tile.

Preview (CSS-only mockup — real version pulls hero photos from your obs):

Why tags, not collections or categories?

User preference. Categories affect URLs (/category/year/.../), which would change post permalinks. Collections add config and live outside _posts/, which is more invasive. Tags are the lightest touch and integrate with whatever existing tag system the blog already has.

Setup guide

Steps to wire this into your real Jekyll blog repo.

1. Copy the files

From this folderTo your blog repo
scripts/inat_sync.rbscripts/inat_sync.rb
workflows/inat-sync.yml.github/workflows/inat-sync.yml
jekyll/observations.htmlobservations.html (site root)

2. Set the repo variable

In your blog repo → Settings → Secrets and variables → Actions → Variables tab, add: 

Name:  INAT_USER
Value: <your iNaturalist user_login>

3. Add to _config.yml

inat_user: <your iNat login>   # used by observations.html for the header link

4. Run the one-time backfill

  1. Go to Actions → iNaturalist sync → Run workflow.
  2. Check the backfill box.
  3. Click run. Wait. Review the resulting commit. If happy, you're done.
  4. If the backfill produced too many posts, revert the commit and tune the script before retrying.

5. Cron takes over

Daily at 07:00 UTC the Action runs, posts anything new, no-ops if nothing.

Open item: the script's USER_AGENT constant has a placeholder URL. Edit it to point to your blog repo so iNat staff can reach you if the script misbehaves.

Risks & gotchas

Stuff that could bite you, ordered by likelihood.

iNat photo URL changes

Photos are hotlinked from inaturalist-open-data.s3.amazonaws.com. If iNat ever migrates this bucket or changes the size-suffix convention, every post on the blog shows broken images. Mitigation: a one-off script to swap the host across all posts. Low probability; high blast radius.

Backfill is irreversible-ish

The first backfill writes one post per observed-on date — could be dozens or hundreds of posts in a single commit. If you're not happy with the formatting, revert and tune the template before retrying. The manifest will have been updated by the failed run, so a retry will see zero new observations — you'll need to git checkout the manifest from before the backfill commit as well.

Geoprivacy edits after publish

If you set an observation to obscured or private after a post is live, the post still shows the original place_guess. We mitigated this by never showing coordinates — only the (already fuzzy) place name — but the place name itself could still be sensitive in some contexts. If this worries you, hand-edit the affected post.

Identification changes after publish

By design, posts are snapshots. If a community ID corrects your species after you've posted, the blog will keep the old name. The post body links back to iNat, where the current ID is canonical.

API outage at run time

Script aborts with a non-zero exit on any non-2xx response. Nothing gets committed. The next day's run picks up where this one stopped.

Workflow not running for 60+ days

GitHub disables scheduled workflows on repos with no activity for 60 days. Since this workflow itself commits to the repo whenever there's new content, that resets the clock — but if you ever go 60 days without uploading to iNat and nobody pushes anything else, the cron stops. Pushing any commit re-enables it.
