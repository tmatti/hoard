What Athena is

A single-user, self-hosted "personal brain." It stores two kinds of records — memories (short atomic facts, embedded whole) and notes (longer documents, chunked into note_chunks and embedded per chunk) — and retrieves them with hybrid keyword + vector search fused by Reciprocal Rank Fusion. The pitch: durable, portable memory for AI tools that isn't locked to any one vendor. Point Claude (or any MCP client) at it over MCP; let any future CLI/web/mobile client use the same REST API against the same Postgres.

The three ideas worth remembering

Everything below is a consequence of three deliberate design choices:

Layering
Adapters over a Brain
api and mcpserver are thin adapters; all logic lives in service (Brain); all SQL lives in store. The dependency arrow only points down.
Guarantee
A write never fails on embedding
Rows persist first with embed_status='pending'; embedding is best-effort with a background retry net. The generated tsvector makes them keyword-findable immediately.
Storage
Two indexes, side by side
Generated tsvector (GIN) and vector(1536) (HNSW cosine) live on the same rows; hybrid search fuses a leg from each. Memories index whole; notes index by chunk.

Storage

Data model — how things are saved

The key asymmetry: memories are indexed whole (one row = one fact = one embedding), while notes are indexed by chunk — the note row keeps the full document for retrieval, but every search index lives on note_chunks. The notes table itself has no tsvector and no embedding.

memories

  • id uuid PK
  • content text — the atomic fact
  • tags text[] GIN
  • source text, optional origin
  • embedding vector(1536) HNSW cos
  • embed_status pending·ok·failed
  • search tsvector GENERATED GIN
  • embed_attempts int · backoff counter
  • embed_last_attempt_at timestamptz · backoff clock
  • created_at / updated_at

notes

  • id uuid PK
  • title text
  • content text — full doc, source of truth
  • tags text[] GIN
  • created_at / updated_at
  • no embedding, no tsvector here — chunks carry both; embed_status is aggregated from chunks at read time

note_chunks

  • id uuid PK
  • note_id FK → notes · ON DELETE CASCADE
  • idx int · UNIQUE(note_id, idx)
  • content text — what gets embedded
  • embedding vector(1536) HNSW cos
  • embed_status pending·ok·failed
  • search tsvector GENERATED GIN
  • embed_attempts int · embed_last_attempt_at timestamptz
Model-drift guard: a single-row embedding_meta table (id bool PK CHECK (id)) records provider / model / dimensions. On first boot Athena adopts the configured dims — ALTER-ing the vector columns and rebuilding the HNSW indexes if they differ from the migration's 1536. On every later boot, any provider/model/dims mismatch is a hard, fail-fast error whose message embeds the exact remediation SQL. EMBEDDING_PROVIDER=none skips the guard.
Indexing asymmetry, precisely: GIN on memories.search, memories.tags, notes.tags, note_chunks.search; HNSW cosine on memories.embedding and note_chunks.embedding; a btree on note_chunks.note_id. The notes table has no search index at all — it's a retrieval-only document store.
Dynamic flow

Saving a memory — remember

The core guarantee: an embedding failure never fails a write. The row persists first; the embedding is best-effort with a background safety net.

agent → mcp remember(content, tags?, source?) — one atomic fact per call (the tool description tells the agent not to batch)
mcp → brain Brain.CreateMemory — the REST POST /v1/memories path lands here too
brain → store/pg INSERT INTO memories with embed_status='pending'. The search tsvector is a GENERATED column — keyword search finds it immediately, embedding or not.
brain → embed api Embed([content]), synchronous under a 10-second context deadline

Embedding succeeds

SetMemoryEmbedding(id, content, vec) — the UPDATE is content-guarded (WHERE id=$1 AND content=$3): if the row changed mid-flight the stale vector is dropped, not written. It also resets embed_attempts=0, embed_last_attempt_at=NULL.

Returned to agent: embed_status='ok'.

Embedding fails / provider = none

MarkMemoryEmbedFailed increments embed_attempts and stamps embed_last_attempt_at; the tool call still returns "Stored memory id=…" with embed_status='failed'.

The retry loop (1-min tick, batches ≤32 across memories + chunks) re-embeds it — first retry immediate, then backoff 4 / 8 / 16 / 32 / 64 min, capped at 1 h, so one broken row never starves the rest.

Why "immediate then backoff": a row is eligible while embed_attempts < 2. A synchronous failure sets attempts to 1, so the very next tick retries with no delay (a transient blip recovers fast). Only after that does the exponential clock 1 min · 2^attempts kick in.
Dynamic flow

Saving a note — create_note

Notes pass through the chunker first; the note and its chunks land in one transaction, then every chunk is embedded in one batched API call.

agent → mcp create_note(title, content, tags?) — for anything longer than an atomic fact
brain → chunk chunk.Split(content): split on blank-line paragraphs, greedily pack to ~1200 chars (hard max 3000, oversized paragraphs split on sentences), and carry the last ≤300 chars into the next chunk as overlap for context continuity
brain → store/pg One transaction: INSERT notes + INSERT note_chunks (idx 0…n, 'pending') — committed before any network call
brain → embed api Embed([all chunk texts]) — one batched call, 10-second deadline

Batch succeeds

SetChunkEmbedding per chunk, each content-guarded. Note returns with embed_status='ok'.

Batch fails

Every chunk is marked failed; the note is saved regardless. On retry, if a batch keeps failing the loop falls back to per-item embedding so one poison chunk can't block the others.

Updates: update_note with new content deletes and re-creates all chunks in the same transaction, then re-embeds. A note's embed_status is never a stored column — it's aggregated on read from its chunks via bool_or: failed if any failed, else pending if any pending, else ok.
Dynamic flow

Search — recall

Hybrid search = a keyword leg and a vector leg, fused with Reciprocal Rank Fusion. Memories and note chunks are searched separately, then merged on a shared score scale. The MCP recall tool always runs hybrid; REST /v1/search also exposes mode=keyword|vector.

Freshness: because the keyword leg reads the generated tsvector and fusion is a FULL OUTER JOIN, a just-written row whose embedding is still pending is findable immediately — the vector leg simply contributes nothing for it yet.

Referencing — results are pointers, not payloads

Follow the reference

recall returns ids and snippets. The agent then calls get_note(note_id) for the full original content — always the note row, never the chunks — or acts on update_note(id) / forget(memory_id). Deleting a note cascades to its chunks; a memory delete is a single row.

Tags are the cross-cutting index

list_tags aggregates counts across memories and notes (UNION ALL + GROUP BY) so the agent reuses vocabulary instead of inventing new tags; every list and search call accepts a tag filter (GIN-indexed text[]).

Drift & under-specification

docs/architecture.md doesn't exist factual miss

The artifact footer says "full Mermaid version committed at docs/architecture.md." There is no docs/ directory in master @ 0bfdac9. The only concrete inaccuracy — likely aspirational, or living on an unmerged branch.

Backoff is driven by a timestamp too enrichment

The data-model tables list embed_attempts but omit embed_last_attempt_at (timestamptz, migration 00003). The eligibility clause needs both: 1 min · 2^LEAST(attempts,6) since the last attempt, capped at 1 h. Sequence from attempts=2: 4, 8, 16, 32, 64→60(cap) min.

"10s timeout" is the context deadline, not the whole story nuance

embedTimeout = 10s is a per-call context.WithTimeout. The OpenAI client also carries its own 30s http.Client timeout. The 10s context cancels first, so the effective bound is 10s — the artifact is functionally right, just under-specified.

Provider enum is openai_compatible | none clarification

"Default OpenRouter" refers to the default base URL (EMBEDDING_BASE_URL), not the provider name. The EMBEDDING_PROVIDER value is literally openai_compatible or none.

The search asymmetry is even sharper than stated enrichment

The notes table has no search tsvector, no embedding, and no stored embed_status — all three live on (or are derived from) note_chunks. Status is computed on read via bool_or. So notes is a pure retrieval-only document store with only a tags index.

The drift guard auto-adapts dimensions on first boot enrichment

EnsureEmbeddingMeta adopts the configured dims on an empty meta row — ALTER-ing the vector(N) columns and rebuilding both HNSW indexes if they differ from the migration's 1536. Only on later boots is a mismatch a hard error, and its message embeds the exact remediation SQL.

Retry ordering prevents structural starvation enrichment

ListPendingEmbeds does a per-leg LIMIT, then UNION ALL, then a global ORDER BY embed_attempts ASC, embed_last_attempt_at ASC NULLS FIRST — deliberately, so memories can't structurally starve note chunks. Fresh/low-attempt rows always flow first.

Guarantees the artifact doesn't mention hardening

Errors are never echoed to clients — /healthz and writeServiceError sanitize DB/provider detail and log the real error server-side. Also: 1 MiB request-body cap, BRAIN_API_KEY ≥ 16 chars, English-only tsvector (keyword ranking weak for non-English; vector unaffected), and PATCH can't null a field.

The retry loop runs in stdio mode too enrichment

go brain.RunEmbedRetryLoop(...) is started before the --stdio branch in main.go, so the background embedding safety net is active in both HTTP and stdio deployments.
