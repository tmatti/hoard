A ractor is an isolated Ruby interpreter inside your process, with its own object heap and its own interpreter lock, so four of them run on four cores at once. On Ruby 4.0.2 that promise finally pays. Four ractors computed four fib(32) calls 3.77× faster than doing them one after another. Four forked processes, the hardware ground truth on the same box, managed 3.80×. Threads returned 0.96×, which is the GVL behaving exactly as documented.

The waiting is a different problem, and it is the one an agent loop is made of. A turn is one LLM call, maybe a tool call, then another LLM call, and almost all of that time is network latency. CRuby releases the GVL while a thread blocks on I/O, so threads already overlap those calls perfectly. Ractors tie them: eight concurrent 300ms calls took 0.31s either way. Fibers under the async gem tie as well, 0.32s against 0.34s for threads over 50 concurrent calls, and they do it on one thread instead of fifty.

So I would split an agent platform along that line. The I/O layer belongs to fibers, because a task costs kilobytes and because Async::Semaphore and Async::Barrier give you a cap on in-flight tool calls and a task tree that cancels together. The CPU stages belong to a ractor pool, which on this Ruby scales like forks without the memory of forks. Pusher publishing stays in the main ractor, because the gem still raises inside one. The interesting engineering is the seam between the fiber side and the ractor side, and tab 05 measures what happens when you get it wrong.

#What changed, and what did not

Three things I expected to fail on 4.0.2 worked on the first try. require inside a ractor works, because Ruby delegates it to the main ractor. net/http works: a request from inside a ractor came back HTTP 200. Timeout.timeout works, which surprised me most, since it is built on a global timeout thread.

I also expected the old multi-thread deadlock to reproduce. It did not. Three threads each spawning a ractor and blocking on #value all returned, and so did eight. That pattern used to wedge the process hard enough to ignore SIGTERM. The fix is recent, so I would still run one load test at your real job concurrency before designing around it, but the shape is no longer forbidden.

What still fails is the ecosystem, not the VM. The pusher gem raises RuntimeError: defined with an un-shareable Proc in a different Ractor the moment you call trigger inside a ractor. Lazy class-level memoization, the most common idiom in Ruby configuration code, raises can not set instance variables of classes/modules by non-main Ractors. Globals stay main-only. Those three account for nearly every real-world port failure I hit.

~/fundamentals  ·  the model, from the ground up

What a ractor actually is

A ractor is an isolated Ruby interpreter living inside your process. It has its own object heap, its own root set, and its own interpreter lock. Threads in CRuby share one heap and one Global VM Lock, which is why they interleave but never run Ruby code on two cores at the same moment. Ractors give up the shared world in exchange for real parallelism, and the VM enforces the trade rather than trusting you to.

The enforcement is total. Two ractors cannot see each other's objects, cannot read each other's globals, and cannot share a mutable cache. Everything crossing between them is deep-copied, moved, or proven immutable first. Most of the friction in this report comes from that one rule meeting a Ruby ecosystem that was written assuming shared state.

#Spawn and result

Ruby 4 dropped Ractor#take and Ractor.yield. Results now come back through #value and #join, which behave like their Thread counterparts, and streaming goes through Ractor::Port. If you last read about ractors a year ago, that is the change to absorb first: Ractor.method_defined?(:take) now returns false.

# A ractor is an isolated interpreter in your process. The block's last
# expression is its result; #value waits for it.
r = Ractor.new(21) { |n| n * 2 }
r.value          # => 42
r.join           # waits for termination, returns the ractor

# Arguments are copied in unless they are already shareable. Integers,
# Symbols, frozen Strings, Classes and Modules cross by reference.

Spawning is cheap but not free. A bare spawn and wait measures around 4ms, which is the cost of a new heap and a native thread. That is fine per HTTP request and ruinous per token, and it is the whole argument for a persistent pool over per-task spawning.

#The block may not capture anything

The block handed to Ractor.new must be isolable. It may not reference a single outer local, because that reference would point from one heap into another. The error message names the variable, which helps, and the way you hit it is often invisible.

# The block may not close over ANY outer local.
x = 10
Ractor.new { x + 1 }
# ArgumentError: can not isolate a Proc because it accesses outer variables (x).

# Pass state in as an argument instead.
Ractor.new(x) { |n| n + 1 }   # fine

# The sneaky version, which cost me an hour: a `rescue => e` earlier in the
# same scope defines an outer local `e` that outlives its own `end`.
begin
  risky!
rescue => e            # outer local `e` now exists for the rest of the scope
end

Ractor.new do
  do_work
rescue => e            # same name, so the block counts as capturing it
  e.message
end
# Fix: name ractor-internal rescue variables distinctly, e.g. `rescue => err`.

The rescue-variable trap

Nothing in the failing block looks wrong. The collision lives in a begin/rescue somewhere above it, and the message reads can not isolate a Proc because it accesses outer variables (e). Every experiment script in tab 10 uses err inside ractor blocks for exactly this reason.

#The inbox and the port

Every ractor has one default inbox. Anyone holding a reference can send into it without blocking, and the owner drains it with Ractor.receive. That channel survived from the old API unchanged, and it is how jobs reach workers.

Everything flowing the other way now goes through Ractor::Port. A port is a first-class shareable queue with one designated receiver, the ractor that created it, and any number of senders. port << value is the push, port.receive is the pull, and calling receive from anywhere else raises only allowed from the creator Ractor of this port. That one sentence dictates the entire agent-loop topology in tab 06, so it is worth reading twice.

# A port is a queue with one designated receiver: the ractor that created it.
# Any ractor may push into it. This is how a worker streams progress out.
port = Ractor::Port.new

w = Ractor.new(port) do |out|
  out << "progress: turn 1"     # << is the push; it does not block
  out << "progress: turn 2"
  :done                         # still the ractor's return value
end

port.receive     # => "progress: turn 1"
port.receive     # => "progress: turn 2"
w.value          # => :done

# port.send(obj, move: true) exists too, for handing over a big object
# without copying it. The sender loses its reference.

#Request and reply

Because only the creator may receive, a request/reply exchange ships the reply port along with the arguments. The worker never creates a port and never receives from one. It reads its inbox and pushes into whatever port the caller handed it, which keeps ownership obvious at every step.

# Requests arrive on the default inbox. The caller ships a reply port
# along with the arguments, and the worker pushes the answer into it.
calc = Ractor.new do
  loop do
    op, a, b, reply = Ractor.receive
    break if op == :stop
    reply << (op == :add ? a + b : a * b)
  end
end

reply = Ractor::Port.new
calc.send([:mul, 6, 7, reply])
reply.receive              # => 42
calc.send([:stop, nil, nil, nil])

A Ractor::Port is shareable, so it travels inside a message without being copied. So is a Ractor itself, including Ractor.current. A worker can therefore mail its own identity to the supervisor, which is the trick the pull-based dispatch in tab 06 is built on.

#Selecting over many sources

Ractor.select takes ractors and ports in the same call and returns the pair [source, message] for whichever fires first. One select loop can therefore drive a whole pool: job requests on one port, results on another, progress events on a third.

# One select loop, three ports, no polling and no sleeping.
until results.size == JOBS && events.size == EXPECTED_EVENTS
  port, msg = Ractor.select(ready_port, results_port, events_port)
  case port
  when ready_port   then msg.send(jobs.shift || :shutdown)  # msg is an idle worker
  when results_port then results << msg
  when events_port  then events << msg
  end
end

#Failure crosses the boundary too

# An unhandled exception does not kill the process. It is re-raised in
# whoever waits on the ractor, wrapped in Ractor::RemoteError.
boom = Ractor.new { raise "agent crashed" }

begin
  boom.value
rescue Ractor::RemoteError => err
  err.cause.class      # => RuntimeError
  err.cause.message    # => "agent crashed"
end

Read the operational consequence carefully. A ractor that raises is gone, and its inbox is orphaned. A supervisor sitting in Ractor.select will simply never hear from it again, and a pool that loses workers silently shrinks toward zero throughput. Supervision is not decoration on a ractor pool. It is the part that keeps the pool alive.

#Globals, constants, class state

Three kinds of shared thing behave differently, and all three show up in the first hour of any real port.

# 1. Global variables belong to the main ractor.
$counter = 0
Ractor.new { $counter += 1 }.value
# Ractor::IsolationError: can not access global variable $counter
#                         from non-main Ractor

# 2. Constants are fine if what they point at is shareable.
MODEL   = "claude-sonnet-5".freeze              # ok, frozen String
HEADERS = { "accept" => "application/json" }     # not ok, mutable Hash
SAFE    = Ractor.make_shareable({ "accept" => "application/json" })

# 3. Class-level mutable state, the standard Ruby memo idiom, is out.
class AgentConfig
  def self.settings
    @settings ||= { "model" => "claude-sonnet-5" }
  end
end
Ractor.new { AgentConfig.settings["model"] }.value
# Ractor::IsolationError: can not set instance variables of
#                         classes/modules by non-main Ractors

# The fix never changes: build it at boot, deep-freeze it, expose a constant.
class AgentConfig2
  SETTINGS = Ractor.make_shareable({ "model" => "claude-sonnet-5" })
end
Ractor.new { AgentConfig2::SETTINGS["model"] }.value   # => "claude-sonnet-5"

The third one will find you. Lazy memoization on a class object is everywhere in Ruby configuration code, and it is illegal from a non-main ractor because it mutates an object every ractor can see. Anything workers read has to exist and be deep-frozen before the first worker spawns. Tab 03 covers what deep-frozen means in practice.

~/shareability  ·  what crosses the boundary, and how

Copy, move, share

Every object that crosses between ractors takes one of three routes. It is deep-copied, so both sides own a separate graph. It is moved, so the sender's reference dies. Or it is proven immutable first and passed by reference, which is the only way two ractors ever point at the same object. Knowing which route a given message takes is most of what it takes to design a message protocol that stays fast.

Experiment 02 asks Ractor.shareable? about ten representative objects. The answers are worth memorising, because two of them are counterintuitive.

Freezing is shallow and shareability is deep. That mismatch produces the single most common surprise in ractor code: a frozen container full of unfrozen contents looks safe, reports frozen? == true, and still cannot cross.

#The three routes, in code

# COPY, the default. send deep-copies the whole object graph, proven here
# by the object_id coming back different on the other side.
msg = { messages: [{ role: "user", content: String.new("hi") }] }
worker.send(msg)
# receiver's msg.object_id != sender's msg.object_id

# MOVE, zero-copy ownership transfer. 10MB crossed without being copied.
big = String.new("x") * 10_000_000
mover.send(big, move: true)
big.bytesize
# Ractor::MovedError: the sender's reference is dead the moment it lands

# SHARE. make_shareable deep-freezes in place, and shareable objects then
# cross by reference: identical object_id on both sides.
config = { model: "claude-sonnet-5", max_tokens: 1024, tools: ["search", "code"] }
Ractor.make_shareable(config)
config.frozen?              # => true
config[:tools][0].frozen?   # => true, it went all the way down

Copying is the right default for agent messages, which are small hashes of strings and symbols. Moving earns its keep exactly once in a typical loop: handing a finished transcript to whatever persists it, where the buffer is large and the sender is done with it. Sharing is for configuration, prompts, tool schemas and anything else built at boot and never touched again.

MovedError is a runtime error, not a compile-time one

Nothing warns you that a variable has been moved out from under you. The next method call on it raises Ractor::MovedError, possibly in an unrelated part of the code that still holds a reference. Move only from a local you are about to drop, and never from anything reachable from a collection someone else can read.

#Two war stories

The frozen array of mutable strings

A tool registry that reads TOOL_NAMES = %w[search calculate].freeze is a frozen array of two unfrozen strings, so the constant is not shareable. Workers referencing it die with IsolationError at the moment they touch it, which is inside the agent loop, one turn in. The supervisor then blocks forever in Ractor.select waiting on workers that no longer exist. Two failures, one cause, and the visible symptom is a hang rather than an error.

# The bug: frozen container, unfrozen contents.
TOOL_NAMES = %w[search calculate].freeze
Ractor.shareable?(TOOL_NAMES)   # => false

# Fix 1, the one-liner every file should have anyway:
# frozen_string_literal: true
#   now the literals are frozen and the array is shareable.

# Fix 2, explicit, for arrays built at runtime:
TOOL_NAMES = Ractor.make_shareable(names.map(&:freeze))

The top-level lambda

Tools written as top-level lambdas cannot be shared, because a proc created at the top level captures main as its self, and main is not shareable. Ruby 4 answers this directly with Ractor.shareable_proc and Ractor.shareable_lambda, which build the proc with a shareable self and refuse to capture locals.

Ractor.make_shareable(->(x) { x + 1 })
# Ractor::IsolationError: Proc's self is not shareable: #<Proc:0x00007f1718d...

# Ruby 4 fix:
sp = Ractor.shareable_proc { |x| x * 10 }
Ractor.shareable?(sp)                              # => true
Ractor.new(out, sp) { |port, f| port << f.call(4) }   # => 40

# The shape I actually ship: a module. Modules are shareable, method
# definitions are shared code rather than data, and this is what a real
# tool registry looks like anyway.
module Tools
  module_function
  def search(args)    = SearchIndex.query(args["q"])
  def calculate(args) = Calculator.evaluate(args["expr"])
end
Tools.public_send(name, args)   # dispatch by string, no proc anywhere

I reach for the module version even where shareable_proc would work. Dispatching by name through public_send keeps the registry as plain data, keeps tool code somewhere a backtrace can name, and sidesteps the whole question of which procs are shareable.

#Make it shareable at boot, once

The pattern that survives contact with a real codebase is a single boot-time file that builds every constant workers will read, deep-freezes it, and asserts the result. Assert rather than hope. A shareability failure discovered at boot is a one-line fix, and the same failure discovered inside a worker is a hang in a supervisor loop.

# frozen_string_literal: true
# config/initializers/agent_shareable.rb, or wherever your boot lives.

module AgentRuntime
  MODEL        = "claude-sonnet-5"
  MAX_TURNS    = 12
  TURN_BUDGET  = 90.0                       # seconds of wall clock per run
  TOOL_NAMES   = Ractor.make_shareable(%w[search calculate fetch].freeze)
  TOOL_SCHEMA  = Ractor.make_shareable(JSON.parse(File.read(SCHEMA_PATH)))
  SYSTEM       = Ractor.make_shareable(File.read(PROMPT_PATH))

  # Fail at boot, not inside a worker three turns into a run.
  constants.each do |c|
    v = const_get(c)
    next if Ractor.shareable?(v)
    raise "AgentRuntime::#{c} is not shareable: #{v.class}"
  end
end

#A message protocol that survives

Messages between the supervisor and its workers are an interface, and they outlive the code on both sides of them. Four rules have held up for me.

Send plain data. Hashes of symbols, strings, integers and arrays copy cheaply and deserialize into anything later. A message carrying a model object carries that object's whole graph, its associations and its dirty state, and the copy will surprise you.

Version every message. A single v: 1 key costs nothing and lets a rolling deploy survive a worker running last release's code. Workers should reject a version they do not understand rather than pattern-match their way through it.

Copy small, move large. Progress events are a few hundred bytes, so copy them and stop thinking about it. A 40MB transcript being handed off for persistence is worth move: true, and the sender should drop the local immediately afterwards.

Share constants only. If a worker needs configuration, it reads a deep-frozen constant that existed before it spawned. If it needs anything that changes, that thing arrives in a message. There is no third category, and pretending there is one is how mutable state creeps back in.

# The job, going out to a worker: plain data, versioned, small.
{ v: 1,
  run_id:   "run_01HQ...",
  agent_id: "agent-7",
  prompt:   "Research ractors, then compute 6*7",
  deadline: 1_766_000_090.0 }         # absolute, monotonic, not a duration

# The event, coming back: small enough to copy on every turn.
{ v: 1, run_id: "run_01HQ...", seq: 41,
  type: "tool.result",
  payload: { tool: "search", duration_ms: 812, preview: "3 results..." } }

~/runtimes  ·  four primitives, two benchmarks

Threads, fibers, ractors, forks

CRuby gives you four ways to have more than one thing in flight, and they answer two different questions. Threads and fibers overlap waiting. Ractors and forks multiply cores. Picking the wrong axis is how people end up disappointed by ractors, so this tab measures both axes on the same box with the same script.

#The GVL, precisely

CRuby holds one Global VM Lock per ractor, and a thread must hold it to execute Ruby bytecode. Threads inside a ractor therefore take turns: they interleave, they never run bytecode simultaneously, and adding threads to a computation adds scheduling instead of speed. Experiment 03 puts a number on it. Four threads running fib(32) took 0.93s against 0.89s serial, which is 0.96×, slightly worse than doing nothing.

The lock is released around blocking operations. A thread waiting on a socket read, a sleep, or most blocking C calls hands the GVL back, so other threads run while it waits. That is why the same threads that cannot speed up arithmetic collapse eight sequential 300ms API calls into one 300ms wall-clock window. Every ractor has its own GVL, which is the whole mechanism behind parallel Ruby. Four ractors means four locks means four cores.

#CPU-bound work, where ractors now match forks

Four fib(32) calls on four cores, done four ways in one script.

Forks reach the same speed, so the argument for ractors is not throughput. It is that ractors share the process. A forked worker needs its own copy of the interpreter and its own connections, cannot hand back a result without serialising through a pipe, and dies invisibly if the parent is not careful. A ractor returns a Ruby object to a Ractor.select loop in the same process, in about 4ms of setup, and its failure arrives as a Ractor::RemoteError you can rescue.

#I/O-bound work, a dead heat

Experiment 04 is the shape of an agent turn: eight LLM calls, each a real blocking TCP round trip against a local server that answers after 300ms.

Fibers get their own tab because they change the resource question rather than the wall-clock one. Tab 05 covers the scheduler, the structured-concurrency primitives, and the one place where mixing fibers and ractors costs you 0.5 seconds.

#Memory and spawn cost

A ractor carries its own heap, so a pool of four is four sets of GC state, four sets of inline caches and four young generations. That is the price of removing the shared lock, and it means pool size is a memory decision as well as a CPU one. Spawn measured around 4ms, which is small next to an LLM call and enormous next to a tool dispatch, so spawn once at boot and keep the workers alive.

Forks trade differently. Copy-on-write keeps the initial cost low, but every page a child writes becomes private, and a Ruby child writing to objects touches a lot of pages. For CPU stages inside an already-loaded Rails process, ractors are the cheaper way to reach the same 3.8×, as long as the code on the hot path can live without shared class state.

~/async  ·  the I/O layer, and the ractor bridge

Async Ruby for the waiting part

The async gem is an implementation of Fiber::Scheduler, the hook CRuby added so a library can take over what happens when Ruby code blocks. Inside an Async block, a socket read, a sleep, a DNS lookup or a Thread::Queue#pop stops parking the thread and parks the fiber instead. The reactor runs something else until the descriptor is ready. There are no async/await keywords, and ordinary blocking code keeps working unchanged.

That last point is what makes fibers practical in Ruby rather than merely elegant. There is no function colouring: Net::HTTP, pg, redis and your own socket code do not need async variants, because the scheduler intercepts at the blocking primitive. A task is a fiber, which costs kilobytes of heap, so thousands of concurrent agent runs in one thread is a normal amount rather than a stunt.

#Same wall time, one thread

Experiment 08 runs 50 concurrent 300ms calls twice: once as 50 threads, once as 50 tasks in one thread.

$ ruby 08_async.rb # ruby 4.0.2, async 2.44.1
50 calls, threads            0.34s
50 calls, async tasks        0.32s
32 calls, semaphore cap 8    1.21s

Threads win nothing and lose nothing on the clock. What changes is what the process is holding: 50 native stacks and 50 scheduler entries against 50 fiber objects. Scale that to a platform running a thousand concurrent agent runs, each mostly idle between LLM round trips, and the difference stops being academic.

# 50 concurrent calls, one thread. No await, no coloured functions:
# llm_call is the same plain blocking socket code the thread version used.
Async do |task|
  N.times.map { task.async { llm_call(PORT) } }.each(&:wait)
end

#Structured concurrency, which threads do not give you

An Async block does not return until the tasks inside it finish, and a task's children belong to it. Cancel the parent and the subtree unwinds with proper ensure semantics. That alone is worth the dependency for an agent loop, where a run that hits its deadline has to abandon whatever fan-out is in flight without leaking a single request.

Two primitives do most of the work. Async::Barrier owns a set of tasks and waits for all of them. Async::Semaphore caps how many run at once, which is exactly the "fan out 32 tool calls, keep at most 8 in flight" constraint that every agent platform eventually needs. Measured: 32 calls of 300ms each through a semaphore of 8 took 1.21s, which is four clean waves.

# A barrier owns the tasks; a semaphore caps how many are in flight.
# 32 calls of 300ms through a cap of 8 measured 1.21s: four waves.
Async do
  barrier   = Async::Barrier.new
  semaphore = Async::Semaphore.new(8, parent: barrier)
  32.times { semaphore.async { llm_call(PORT) } }
  barrier.wait
end

Getting the same behaviour from threads means a fixed pool, a work queue, a way to propagate cancellation into a blocked Net::HTTP call and a way to be sure you did not leave a worker holding a half-written request. The fiber version is four lines and the cancellation semantics come with the scheduler.

#Where async gives you nothing

One thread means one core. Async does not touch the CPU question at all, and anything that blocks the thread rather than the fiber stops every task in the reactor. Three things do that: a C extension that does not release the GVL, a tight pure-Ruby loop with no blocking call in it, and any ractor operation, because Ractor#value and Ractor::Port#receive are not scheduler-aware.

I measured the third one because it is the exact mistake a hybrid design invites. One task waits on a ractor doing 0.5s of CPU work while a sibling task makes a 0.3s call. They should overlap and finish in 0.5s. They ran serially instead, for 0.80s.

# The mistake. Ractor#value is not scheduler-aware, so this blocks the
# whole reactor thread and the sibling task never gets to run.
Async do |task|
  a = task.async { Ractor.new { sleep 0.5; :cpu_done }.value }  # blocks the thread
  b = task.async { llm_call(PORT) }                            # should overlap, cannot
  [a, b].each(&:wait)
end
# 0.80s: 0.5s of ractor wait plus 0.3s of I/O, one after the other.

#The bridge, an owner thread and a queue

The fix is a seam. One ordinary thread owns the ractor pool and is the only place any ractor method is called. Async code talks to that thread through Thread::Queue, and this is the part that makes the whole design work. Queue#pop is scheduler-aware, so a fiber waiting on a reply parks itself and the reactor keeps serving every other task.

# One owner THREAD runs the ractor pool. Async code hands it work through
# a Thread::Queue, whose #pop parks the fiber rather than the thread.
inbox = Queue.new
owner = Thread.new do
  pool_port = Ractor::Port.new
  loop do
    payload, reply = inbox.pop
    break if payload == :stop
    Ractor.new(pool_port, payload) { |out, n| out << [n, n * 2] }
    reply << pool_port.receive
  end
end

Async do |task|
  a = task.async do
    reply = Queue.new
    inbox << [21, reply]
    reply.pop        # the fiber parks here; the reactor keeps running
  end
  b = task.async { llm_call(PORT) }
  a.wait            # => [21, 42]
  b.wait
end
# 0.30s: the I/O call and the ractor work overlapped.

The rule, short enough for a code review

No fiber may call a Ractor method. Ractors are owned by one thread, that thread talks to the async world through queues, and the async world never learns that ractors exist. The same rule protects Sidekiq job threads in tab 08, for a different reason.

A production owner thread does more than this sketch. It keeps a persistent pool instead of spawning per request, it uses one reply port per pool rather than one per job, and it tags each job so replies reach the right waiter. The seam is the same either way: queues in, queues out, ractor calls confined to one thread.

The consequence for architecture is real. A worker ractor is not restricted to one thing at a time. It can run its own reactor and fan out the tool calls for its run, then do the CPU-heavy part of a tool right there on its own core. That is the hybrid worker described in tab 06: fibers inside for the waiting, a ractor outside for the core.

#The rest of the ecosystem

async-http is the HTTP client built for this stack, with persistent connections and streaming response bodies, which is the right shape for reading a token stream off an LLM endpoint. falcon is the server: one fiber per request instead of one thread, so a request that spends its life waiting on an upstream costs a fiber rather than a thread. I did not benchmark either one here, so treat both as pointers rather than results.

What to check before adopting it

The scheduler covers Ruby-level blocking. A C extension that blocks without releasing the GVL still stops the reactor, and a few database drivers are in that category depending on how they were built. Test your actual driver under an Async block with a second task doing timed work, the same way experiment 08 tested Ractor#value. If the second task's timings go serial, that driver blocks the thread.

~/agent-loops  ·  the architecture, with the real code

A pool of agent workers, driven by one select loop

An agent loop is small. Send the transcript to the model, read the response, run a tool if the model asked for one, append the result, repeat until the model answers or you hit a cap. Everything hard about running it at scale is outside that loop: how many run at once, where each one's CPU work lands, how progress reaches the browser, and what happens when one of them dies.

#Where a turn spends its time

In the shape I care about, one turn is an LLM round trip, sometimes a tool call, and a few hundred microseconds of Ruby. The model call dominates by orders of magnitude, which is why tab 05 puts the loop on fibers. The parts worth moving to a ractor are the ones that burn CPU without waiting: chunking a fetched document, scoring or reranking candidates, computing similarity over embeddings, parsing something large, or a tool that does real arithmetic. Those stages are where the 3.77× from tab 04 turns into wall time you can feel.

Experiment 05 runs the whole thing with a deterministic fake model, so the topology is measured rather than the network. The fake call sleeps 50ms plus 10ms per message in the transcript, calls search on turn one and calculate on turn two, then answers. Eight agents at three turns each, on four workers, finished in 0.55s with all 48 events accounted for.

#The topology

Port receive is creator-only, and that single rule fixes the design. Workers cannot receive from a jobs port the supervisor created, so jobs cannot be handed out that way. What works instead is the inverse. The supervisor creates three ports and receives from all of them, and workers reach the supervisor by pushing. Dispatch runs backwards through a ready_port. An idle worker pushes Ractor.current into it, the supervisor receives that worker and sends the job straight to the worker's own inbox.

Why pull, not round-robin

Handing job i to worker i mod N is the obvious design and the wrong one. Agent runs have wildly different durations: one answers in two turns, the next spends ninety seconds inside a tool. Under fixed assignment, jobs queued behind the slow one wait while three workers sit idle. Because a worker only appears on the ready port when it has nothing to do, the pull version gets work-stealing behaviour with no scheduler code and no queue depth to tune.

Ractor references travel

Ractor.current is shareable, so a worker can mail its own identity to the supervisor and the supervisor can call send on what comes back. Ports are shareable too, which is what lets a worker push an event from the middle of a turn without going back through anybody.

# The agent loop. Ordinary Ruby; the only ractor-aware part is pushing small
# frozen event hashes into the events port.
def run_agent(job, events)
  agent_id = job[:agent_id]
  messages = [{ role: :system, content: SYSTEM_PROMPT },
              { role: :user,   content: job[:prompt] }]
  events << { agent_id:, type: "agent.started" }
  turn = 0
  loop do
    turn += 1
    response = fake_llm(messages)
    messages << response
    if (tc = response[:tool_call])
      events << { agent_id:, type: "tool.called", tool: tc[:name] }
      raise "unknown tool #{tc[:name]}" unless TOOL_NAMES.include?(tc[:name])
      result = Tools.public_send(tc[:name], tc[:args])
      messages << { role: :tool, name: tc[:name], content: result }
      events << { agent_id:, type: "tool.result", tool: tc[:name], preview: result[0, 40] }
    else
      events << { agent_id:, type: "agent.completed", turns: turn }
      return { agent_id:, turns: turn, answer: response[:content], messages: messages.size }
    end
  end
end

Notice how little of this is ractor code. One argument is a port, and events go into it with <<. Everything else is the loop you would have written anyway, which is the property to aim for. The isolation rules should show up at the edges of your framework, never through the middle of its logic.

# and get their job on their own inbox.

  end

The drain condition, learned the hard way

My first version of that loop stopped at results.size == JOBS and lost events. A result and its own trailing agent.completed travel on different ports, and nothing orders one against the other, so the eighth result can arrive before the events behind it. The fix in a script is to wait for both counts. In production it does not come up, because the drain never stops running. Order is guaranteed per worker, which is all a per-run event stream needs.

#The hybrid worker

Async runs inside a ractor, measured in tab 05, so a worker is not limited to one thing at a time. Give it a reactor and it can fan out the tool calls for its own run, then do the CPU-heavy part of a tool right there on its own core. That is the combination the two halves of this report were pointing at: fibers inside the worker for waiting, ractors across workers for cores.

# A worker that overlaps its own tool I/O and still owns a core.
Ractor.new(ready_port, results_port, events_port) do |ready, results, events|
  require 'async'
  require 'async/semaphore'

  loop do
    ready << Ractor.current
    job = Ractor.receive
    break if job == :shutdown

    result = Async do
      # Waiting work: several tool calls at once, capped.
      sem = Async::Semaphore.new(4)
      docs = job[:urls].map { |u| sem.async { fetch(u) } }.map(&:wait)

      # CPU work: no reactor involved, and this ractor owns its own core.
      chunks = docs.flat_map { |d| chunk_and_score(d, job[:query]) }
      events << { agent_id: job[:agent_id], type: "tool.result", n: chunks.size }
      rank(chunks).first(10)
    end.wait

    results << { agent_id: job[:agent_id], top: result }
  end
end

One caution, which follows from the same measurement: inside that reactor, nothing may block the thread. The worker's own CPU section is fine because no other task is waiting on it, but if you add a second concurrent task you have recreated the 0.80s problem inside a ractor instead of in the main process.

#Fitting it to a home-rolled framework

Five rules carry most of the weight when the prototype above becomes part of a real framework.

Build every shared thing at boot

Prompts, tool schemas, model names, retry tables and limits get built once, deep-frozen with Ractor.make_shareable, and asserted at boot as shown in tab 03. If it changes per run, it belongs in the job message instead.

Keep per-run state inside the worker

The transcript, the turn counter, the tool results and the retry bookkeeping live in worker-local variables for the duration of the run. Nothing outside the worker reads them. What leaves is a small event or a final result, both plain data.

Supervise, and respawn

A ractor that raises is gone, and the pool silently shrinks. Worse, a select loop over ports never notices. A dead worker simply stops announcing itself on the ready port, and throughput drops without an error anywhere. Catch failures inside the worker so they arrive as data, and put a monitor thread on each worker for the cases that get past that.

# Inside the worker: a crash becomes an event, not a dead ractor.
begin
  results << run_agent(job, events)
rescue => err
  events  << { agent_id: job[:agent_id], type: "agent.failed",
               error: err.class.name, message: err.message[0, 200] }
  results << { agent_id: job[:agent_id], failed: true }
end

# In the main ractor: one monitor thread per worker. #join returns when the
# worker stops, and a crash surfaces as Ractor::RemoteError with #cause set.
def supervise(worker, ports)
  Thread.new do
    begin
      worker.join
    rescue Ractor::RemoteError => err
      Metrics.increment("agent.worker.died")
      report(err.cause)
    end
    supervise(spawn_worker(*ports), ports)   # replace it and keep watching
  end
end

Several threads blocking on ractor operations used to wedge the process, which would have ruled this pattern out. On 4.0.2 it does not. Eight threads waiting on ractors all returned cleanly. See tab 08 for the measurement and the caveat I would still attach to it.

Make turns idempotent

A run that is retried after a worker death should not double-charge a tool or duplicate a database write. Key each turn by [run_id, turn], make tool side effects idempotent on that key, and the retry becomes boring.

Cap turns and set a deadline

Two limits, not one. A turn cap stops the model looping on a tool that keeps failing. An absolute wall-clock deadline, computed at enqueue and carried in the job, stops a run that is technically making progress from occupying a worker forever. Compare against Process.clock_gettime(Process::CLOCK_MONOTONIC) at the top of each turn.

Pool sizing

Workers compete with everything else in the process for the same cores. On a 4-core box running Puma and Sidekiq, a pool of 4 CPU-bound ractors will fight the request threads for the machine. Size the pool to the cores you can spare, not to the cores you have, and remember each ractor carries its own heap. My default is cores - 1 in a dedicated worker process and something smaller wherever web traffic shares the box.

~/pusher  ·  streaming progress to the browser

One publisher, in the main ractor

A user watching an agent work wants to see the turns as they happen: the tool that was called, the document that came back, the answer forming. That means events leaving the process while the run is still going, which means deciding who is allowed to talk to Pusher. On Ruby 4.0.2 the answer is narrower than the VM requires, and I think that is the right call.

#What was measured

Two results from experiment 06, and they point in opposite directions.

$ ruby 06_pitfalls.rb # ruby 4.0.2
net/http from ractor: HTTP 200 body={"ok":true}
pusher trigger in ractor: RuntimeError: defined with an un-shareable Proc in a different Ractor

net/http works inside a ractor now. That used to fail on Net::HTTP::SSL_IVNAMES, and freezing those constants only moved the failure to Timeout::TIMEOUT_THREAD. Both are fixed. Timeout.timeout also runs inside a ractor on 4.0.2. So a worker could, technically, publish its own events over HTTP.

The pusher gem still cannot. Pusher::Client.new succeeds and trigger raises, because httpclient underneath it holds procs defined in another ractor. That is a gem-level problem, not a VM one, and no amount of freezing your own constants fixes it.

#Do not publish from workers anyway

Suppose the gem were fixed tomorrow. I would still keep publishing in the main ractor, because the publisher is where four operational concerns live and none of them wants to be replicated across four isolated heaps.

Credentials and configuration are one. A single client, built at boot, with one place to rotate a key. Batching is the second. Pusher accepts up to ten events per trigger_batch call, and ten events per call only helps if one component sees all of them. Coalescing is the third, and it is the one that matters most for agent UIs, where token deltas arrive faster than any browser needs them. Backpressure is the fourth. When Pusher is slow, exactly one queue should grow, and exactly one policy should decide what to drop.

The seam also survives a transport swap. Workers emit plain event hashes and know nothing about who consumes them, so moving to Ably, AnyCable or ActionCable means rewriting one method.

#The seam, end to end

Workers push events into the events port. One thread in the main ractor drains that port and hands each event to the publisher. The publisher batches and calls Pusher. Nothing inside a ractor ever holds an HTTP client.

# Two roles in the MAIN ractor:
#   drain      the only thing that receives from events_port
#   publisher  the only thing that talks to Pusher
# Worker ractors touch neither. They call events << event and move on.

events_port = Ractor::Port.new
publisher   = EventPublisher.new(Pusher::Client.new(**PUSHER_CONFIG)).tap(&:run)

drain = Thread.new do
  loop { publisher.publish(events_port.receive) }
end

On an async stack this is a task rather than a thread. Port#receive blocks the thread and is not scheduler-aware, so the drain keeps its own thread and hands events to the reactor through a Thread::Queue, exactly the bridge measured in tab 05. The publisher itself, which is all socket I/O, is a natural async task.

# frozen_string_literal: true
# The publisher owns the Pusher client and lives in the main ractor.
# Workers never see it; they only push frozen event hashes at a port.

class EventPublisher
  BATCH_MAX = 10      # Pusher accepts 10 events per trigger_batch call
  FLUSH_MS  = 80      # coalesce bursty deltas into one round trip
  QUEUE_MAX = 10_000  # backpressure ceiling

  TERMINAL = ["agent.completed", "agent.failed"].freeze

  def initialize(client)
    @client = client
    @queue  = SizedQueue.new(QUEUE_MAX)
  end

  # Called from the drain thread, never from inside a ractor.
  def publish(event)
    @queue.push(event, true)          # non-blocking: raise rather than stall
  rescue ThreadError
    # Full. Drop coalescible progress; a terminal event waits its turn.
    if TERMINAL.include?(event[:type])
      @queue.push(event)
    else
      Metrics.increment("events.dropped")
    end
  end

  def run
    @thread = Thread.new do
      batch    = []
      deadline = monotonic + (FLUSH_MS / 1000.0)
      loop do
        event = pop_with_timeout([deadline - monotonic, 0].max)
        batch << to_pusher(event) if event
        next unless batch.size >= BATCH_MAX || monotonic >= deadline
        flush(batch)
        batch    = []
        deadline = monotonic + (FLUSH_MS / 1000.0)
      end
    end
  end

  private

  def flush(batch)
    return if batch.empty?
    @client.trigger_batch(batch)
  rescue Pusher::Error => err
    Rails.logger.warn("pusher: #{err.class}: #{err.message}")   # never kill the loop
  end

  def to_pusher(event)
    { channel: "private-agent-run-#{event[:run_id]}",
      name:    event[:type],
      data:    event[:payload] }
  end

  def monotonic = Process.clock_gettime(Process::CLOCK_MONOTONIC)
end

Never drop a terminal event

Under backpressure it is fine to drop or merge message.delta and progress events, because the next one supersedes them. It is never fine to drop agent.completed or agent.failed. A UI that never hears the run ended spins forever. Terminal events block instead of dropping, and they are written to the database as well, so the reconnect endpoint can tell the truth.

~/sidekiq-puma  ·  where this actually runs

Sidekiq owns the run, Puma never does

Sidekiq runs jobs on a pool of threads. Puma serves requests on a pool of threads. Both invite the same pattern: spawn a ractor per unit of work and block until it answers. That pattern used to wedge the whole process. On 4.0.2 it does not, and the reasons to avoid it now are ordinary engineering reasons rather than a landmine.

#The deadlock is gone

Experiment 07 exists to reproduce an old failure: several threads each spawning a ractor and blocking on its result at the same time. On earlier Rubies three threads were enough to wedge the process so thoroughly that it ignored SIGTERM. I expected it to reproduce. It did not.

The fix is recent and the script above is small. Before I designed a production system around concurrent ractor waits, I would run the real job class at real Sidekiq concurrency for a few minutes and watch for a stall. That is one afternoon against a failure mode that historically needed kill -9.

#Still use a pool, and one seam

Per-job spawning costs about 4ms and a fresh heap every time, and it puts GC pressure and pool sizing outside your control: 25 Sidekiq threads spawning ractors freely is 25 interpreters competing for cores that a 4-core box does not have. A persistent pool sized to the cores you can spare fixes both. It also gives you one place to observe queue depth, one place to respawn a dead worker, and one place to shed load when the pool is saturated.

# frozen_string_literal: true
# One pool per process. Jobs hand work to it and wait on their own Queue.

class RactorPool
  include Singleton

  SIZE = Integer(ENV.fetch("RACTOR_POOL_SIZE", "3"))   # cores you can spare

  def initialize
    @inbox = Queue.new
    @owner = Thread.new { run_owner }
    @owner.name = "ractor-pool-owner"
  end

  # Called from any job thread. Blocks that thread only.
  def compute(payload, timeout: 30)
    reply = Queue.new
    @inbox << [payload, reply]
    Timeout.timeout(timeout) { reply.pop }
  end

  private

  def run_owner
    ready   = Ractor::Port.new
    results = Ractor::Port.new
    SIZE.times { spawn_worker(ready, results) }
    pending = {}                                # job id => reply queue
    idle    = []

    loop do
      # Feed idle workers from the inbox, then wait for whatever comes first.
      dispatch(idle, pending) until idle.empty? || @inbox.empty?
      port, msg = Ractor.select(ready, results)
      case port
      when ready   then idle << msg
      when results then pending.delete(msg[:id])&.push(msg[:value])
      end
    end
  end
end

#The Rails caveat

Rails is not ractor-safe and nothing on the horizon changes that. Lazy class-level memoization raises can not set instance variables of classes/modules by non-main Ractors, which is the idiom underneath most of the framework's caches. Autoloading resolves constants by mutating class objects. Rails.logger, Rails.cache and every ActiveRecord connection are shared mutable state by design.

So the boundary is a data boundary. Load records in the job thread, turn them into plain hashes and arrays, send those to the pool, get plain data back, and write it in the job thread. Anything that wants to log from inside a worker emits an event instead and lets the main side log it.

#Puma

Agent loops never run inside a request. A run takes seconds to minutes, and a Puma thread held that long is a thread not serving anyone. The controller creates the run, enqueues the job, and returns the run id plus the channel name so the browser can subscribe before the first event arrives.

If a request genuinely needs a CPU stage, a Puma thread may call the same pool, and the seam is the same one. Keep a timeout on it and decide what a pool-saturated response looks like before you ship it, because a web request queued behind four busy ractors is a slow page rather than a 500.

Falcon changes the shape but not the rules. There the request is a fiber, so a slow upstream costs a fiber rather than a thread, and the pool seam becomes even more valuable. A fiber blocking on Ractor#value stops the whole reactor, while a fiber blocking on Queue#pop parks politely. That is the measurement from tab 05, arriving in your web tier.

Shorter than the list of what fails, and longer than it used to be.

  • Ractor and Ractor::Port references, passed as arguments or inside messages.

#Should you use ractors here?

#Production checklist

Boot

  • Every constant workers read is built at boot and passed through Ractor.make_shareable.
  • A boot-time loop asserts Ractor.shareable? on all of them and raises with the constant's name.
  • # frozen_string_literal: true at the top of every file that defines a shared constant.
  • Tools live in modules with module_function, dispatched by name, never as top-level lambdas.
  • The pool spawns once, sized from an environment variable, with a name on each ractor for the logs.

Design

  • Messages are plain data: hashes, arrays, strings, symbols, numbers. No model objects.
  • Every message carries a version key so a rolling deploy survives mixed worker code.
  • Events are small enough to copy freely and stay under the 10KB transport limit.
  • Large payloads move with move: true from a local that is dropped immediately after.
  • The I/O layer is fibers or threads. Ractors handle CPU stages only.
  • No fiber calls a Ractor method. One owner thread owns the pool, and queues cross the seam.

Supervision

  • Workers rescue their own failures and report them as events, so a crash is data rather than a missing worker.
  • A monitor thread joins each worker and respawns it, treating Ractor::RemoteError#cause as the real error.
  • Every run has a turn cap and an absolute wall-clock deadline carried in the job.
  • Turns are idempotent per [run_id, turn], so a retry after a worker death is safe.
  • Terminal events are never dropped under backpressure, and are persisted as well as published.

Operations

  • Pin the Ruby version. Ractor is experimental and its behaviour changed substantially in this release.
  • Re-run the experiments folder against every Ruby upgrade before it reaches production.
  • Load-test concurrent ractor waits at your real Sidekiq concurrency once, since that fix is recent.
  • Prefer an explicit deadline over Timeout.timeout for agent turns. Timeout works inside ractors now, but a deadline composes with streaming and does not interrupt a half-written request.
  • Export pool metrics: queue depth, workers alive, jobs per worker, respawn count.
  • Alert on a shrinking pool. It is the failure mode that produces no errors, only slowness.

# 05: Agent loops on ractors, Ruby 4 port topology.
#
#   main (supervisor)
#     creates ready_port    workers announce themselves when idle
#             results_port  workers push finished runs
#             events_port   workers stream progress (the Pusher seam)
#
# A port's receive side belongs to the ractor that created it, so all three
# ports are received in main. Job dispatch is pull-based: an idle worker
# pushes itself into ready_port, the supervisor sends it a job on its inbox.
# One Ractor.select watches all three ports at once.

# tool registry has. (A top-level lambda captures `main` as self and cannot
# be shared; Ractor.shareable_proc exists if you need a closure.)
module Tools
  module_function
  def search(args)    = "3 results for #{args["q"].inspect}: [ractors, ports, gvl]"
  def calculate(args) = eval(args["expr"]).to_s # demo only!
end

SYSTEM_PROMPT = "You are a research agent. Use tools, then answer."

# Deterministic fake LLM: search on turn 1, calculate on turn 2, then answer.
# sleep stands in for network and inference latency.
def fake_llm(messages)
  sleep(0.05 + messages.size * 0.01)
  case messages.count { |m| m[:role] == :assistant }
  when 0 then { role: :assistant, tool_call: { name: "search",    args: { "q" => "ractor agent loops" } } }
  when 1 then { role: :assistant, tool_call: { name: "calculate", args: { "expr" => "6 * 7" } } }
  else        { role: :assistant, content: "Answer: ractors give parallel agent loops; 6*7=42." }

end

# The agent loop. Ordinary Ruby; the only ractor-aware part is pushing small
# frozen event hashes into the events port.
def run_agent(job, events)
  agent_id = job[:agent_id]
  messages = [{ role: :system, content: SYSTEM_PROMPT }, { role: :user, content: job[:prompt] }]
  events << { agent_id:, type: "agent.started" }
  turn = 0
  loop do
    turn += 1
    response = fake_llm(messages)
    messages << response
    if (tc = response[:tool_call])
      events << { agent_id:, type: "tool.called", tool: tc[:name] }
      raise "unknown tool #{tc[:name]}" unless TOOL_NAMES.include?(tc[:name])
      result = Tools.public_send(tc[:name], tc[:args])
      messages << { role: :tool, name: tc[:name], content: result }
      events << { agent_id:, type: "tool.result", tool: tc[:name], preview: result[0, 40] }
    else
      events << { agent_id:, type: "agent.completed", turns: turn }
      return { agent_id:, turns: turn, answer: response[:content], messages: messages.size }
    end
  end
end

JOBS      = 8

results_port = Ractor::Port.new
events_port  = Ractor::Port.new

workers = POOL_SIZE.times.map do |i|
  Ractor.new(ready_port, results_port, events_port, name: "worker-#{i}") do |ready, results, events|
    loop do
      ready << Ractor.current          # announce: idle, send me work
      job = Ractor.receive
      break if job == :shutdown
      results << run_agent(job, events)
    end
    :stopped
  end
end

# frozen_string_literal: true
# 08: Async Ruby (the async gem, a Fiber::Scheduler implementation) as the
# I/O layer for agent loops, and how it composes with ractors.
#
# Fibers give I/O concurrency like threads do, but a task costs kilobytes
# instead of a native thread, and you can run thousands in one thread.
# No CPU parallelism: everything runs on one core. That is ractors' job.
Warning[:experimental] = false
STDOUT.sync = true
require 'socket'
require 'async'
require 'async/semaphore'
require 'async/barrier'

puts "#{RUBY_VERSION}, async #{Async::VERSION}"

PORT = 43_212
Thread.new do
  server = TCPServer.new('127.0.0.1', PORT)
  loop do
    c = server.accept
    Thread.new(c) { |cl| cl.gets; sleep 0.3; cl.puts "ok"; cl.close }
  end
end
sleep 0.2

def llm_call(port)
  s = TCPSocket.new('127.0.0.1', port)
  s.puts "POST /v1/messages"
  resp = s.gets
  s.close
  resp
end

def bench(label)
  t0 = Process.clock_gettime(Process::CLOCK_MONOTONIC)
  yield
  puts format("%-28s %.2fs", label, Process.clock_gettime(Process::CLOCK_MONOTONIC) - t0)
end

# A. 50 concurrent calls: 50 threads vs 50 fiber tasks in ONE thread.
N = 50
bench("#{N} calls, threads") do
  Array.new(N) { Thread.new { llm_call(PORT) } }.each(&:join)
end
bench("#{N} calls, async tasks") do
  Async do |task|
    N.times.map { task.async { llm_call(PORT) } }.each(&:wait)
  end
end

# B. Structured concurrency: a barrier owns the tasks, a semaphore caps how
# many run at once. This is the shape of "fan out 32 tool calls, at most 8
# in flight", which no thread pool gives you this directly.
bench("32 calls, semaphore cap 8") do
  Async do
    barrier   = Async::Barrier.new
    semaphore = Async::Semaphore.new(8, parent: barrier)
    32.times { semaphore.async { llm_call(PORT) } }
    barrier.wait
  end
end

# C. Does async run INSIDE a ractor?
r = Ractor.new(PORT) do |port|
  require 'async'
  Async do |task|
    3.times.map { task.async { llm_call(port) } }.each(&:wait)
  end
  "async inside ractor: OK (3 concurrent calls)"
rescue => e
  "async inside ractor: #{e.class}: #{e.message[0, 70]}"
end
puts r.value

# D. The hybrid question: does waiting on a ractor block the whole reactor?
# Ractor#value and Port#receive are not scheduler-aware. While one task waits
# on a ractor, every other fiber in that thread stops too. Measure it.
bench("ractor wait inside async") do
  Async do |task|
    a = task.async { Ractor.new { sleep 0.5; :cpu_done }.value } # blocks the thread
    b = task.async { llm_call(PORT) }                            # should overlap, can't
    [a, b].each(&:wait)
  end
end
puts "  (0.8s = the 0.5s ractor wait blocked the 0.3s I/O call; no overlap)"

# E. The bridge that works: one owner THREAD runs the ractor pool; async code
# talks to it through Thread::Queue, whose #pop parks the fiber, not the
# thread. I/O keeps flowing while the CPU work runs in parallel.
inbox = Queue.new
owner = Thread.new do
  pool_port = Ractor::Port.new
  loop do
    payload, reply = inbox.pop
    break if payload == :stop
    Ractor.new(pool_port, payload) { |out, n| out << [n, n * 2] } # stand-in CPU work
    reply << pool_port.receive
  end
end

bench("owner-thread bridge") do
  Async do |task|
    a = task.async do
      reply = Queue.new
      inbox << [21, reply]
      reply.pop # fiber parks here; the reactor keeps running
    end
    b = task.async { llm_call(PORT) }
    puts "  cpu result via bridge: #{a.wait.inspect}"
    b.wait
  end
end
inbox << [:stop, nil]
owner.join
puts "  (0.3s: the I/O call and the ractor work overlapped)"
