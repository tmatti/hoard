Ruby Ractors for Agent Loops

An empirical report. Seven experiments, three Ruby versions, one 4-core box.

Ractors are real parallel Ruby: each one is an isolated interpreter with its own object heap and its own lock, so N ractors genuinely use N cores. That is the promise. The measured reality on Ruby 3.3 and 3.4 is that CPU-bound work spread across four ractors ran 0.43× the speed of doing it serially — slower, not faster — that stdlib HTTP cannot execute inside a ractor at all, and that two threads waiting on ractors at the same time can wedge the whole process so hard it ignores SIGTERM. Ruby 4.0, released 2025-12-25, changes the arithmetic completely: the same benchmark returned 3.74×, and the new Ractor::Port API removes most of the sharp edges in the messaging model.

For an agent platform today, the honest architecture is unglamorous. The agent loop itself is 99% network wait, and threads already overlap network wait perfectly — the I/O benchmark below has threads and ractors finishing in the same 0.31s. So: run the loop on threads, keep every LLM call, tool call, database write and Pusher trigger in ordinary thread-land, and reserve ractors for the parts that are genuinely CPU-bound — parsing, embedding math, ranking, chunking, tool-side computation — behind a single owner thread per process. On Ruby 4.0 and later, a ractor-per-agent-loop worker pool stops being a science project and becomes a reasonable design.

Officially experimental

Ractors are still marked experimental in CRuby; every run in this report emits the warning unless you silence it with Warning[:experimental] = false. That is not a reason to avoid them, but it is a reason to pin your Ruby version, keep the parallel surface small, and re-run your own compatibility tests on every upgrade.

~/fundamentals  ·  the model, from the ground up

What a ractor actually is

A ractor — "Ruby Actor" — is an isolated Ruby interpreter living inside your process. It has its own object heap, its own root set, and crucially its own interpreter lock. Threads in CRuby share one heap and one Global VM Lock, which is why they interleave but never truly run Ruby code in parallel. Ractors trade that shared world away: no shared mutable state, enforced by the VM rather than by convention, and in exchange they run on separate cores at the same time.

The trade is total. Two ractors cannot see each other's objects, cannot touch each other's globals, and cannot mutate a shared cache. Everything they exchange goes through message passing, and every message either gets deep-copied, gets moved (and taken away from the sender), or is proven immutable first. Most of the friction in this report comes from that one rule meeting a Ruby ecosystem that was built assuming shared state.

#Spawn and result

# A ractor is an isolated Ruby interpreter inside your process:
# its own object heap, its own lock, its own root of reachability.
r = Ractor.new(21) do |n|
  n * 2          # the block's last expression is the ractor's result
end

r.take           # => 42   (Ruby 3.x: #take blocks until the value is ready)

# Arguments are copied in unless they are already shareable.
# Integers, Symbols, frozen Strings, Classes and Modules cross by reference.

Spawning is cheap but not free: a bare Ractor.new {}.take measured 0.004s, about 3–4 milliseconds of setup for a new heap and native thread. That is fine per request and ruinous per token, which is the whole argument for pools over per-task spawning. The same experiment showed a lone ractor running at full speed — fib(30) took 0.096s inside a ractor versus 0.099s in the main ractor — so nothing about being in a ractor is inherently slow. It is the simultaneity that costs, as tab 04 shows.

#The block may not capture anything

The block you hand to Ractor.new must be isolable: it may not reference a single outer local variable, because doing so would create a reference from one heap into another. The error is clear, and the way you hit it is often not.

# The block must be *isolable*: it may not close over ANY outer local.
x = 10
Ractor.new { x + 1 }
# ArgumentError: can not isolate a Proc because it accesses outer variables (x).

# Pass state in as an argument instead:
Ractor.new(x) { |n| n + 1 }   # fine

# The sneaky version of the same rule, hit for real in 01_basics.rb:
# a `rescue => e` variable inside the block collides with an outer `e`
# left over from an earlier begin/rescue, and the block stops being isolable.
begin
  risky!
rescue => e            # <- outer local `e` now exists for the rest of the scope
end

Ractor.new do
  do_work
rescue => e            # <- same name: Ractor.new refuses the block
  e.message
end
# Fix: name ractor-internal rescue variables distinctly (`rescue => err`).

The rescue-variable trap

This cost real debugging time. A rescue => e earlier in the same scope defines an outer local named e that survives the end. A later ractor block that happens to also use rescue => e is then treated as capturing it, and Ractor.new rejects the block with ArgumentError: can not isolate a Proc because it accesses outer variables (e). Nothing in the block looks wrong; the collision is invisible.

#Two mailboxes: push and pull

Ruby 3.x gives every ractor two distinct channels, and mixing them up is the source of most "why is this hanging" moments. The incoming port is an unbounded queue: anyone can send into it without blocking, and the owner drains it with Ractor.receive. The outgoing side is not a queue at all — it is a rendezvous. Ractor.yield blocks until someone calls take, and take blocks until someone yields.

# PUSH: r.send(msg) -> Ractor.receive
#   The incoming port is an unbounded queue. `send` never blocks;
#   `Ractor.receive` blocks until something arrives. Fan-in.
#
# PULL: Ractor.yield(val) -> r.take
#   A rendezvous: `yield` blocks until some other ractor takes the value,
#   and `take` blocks until some value is yielded. Fan-out / load balancing.

echo = Ractor.new do
  loop do
    msg = Ractor.receive            # <- incoming port (push)
    break if msg == :stop
    Ractor.yield("echo: #{msg}")    # <- outgoing yield (pull)
  end
end

echo.send("hello")
echo.take        # => "echo: hello"
echo.send(:stop)

# Because `take` is a rendezvous, N workers can all call `pipe.take` on one
# queue ractor and the VM hands each job to whichever worker asks first.
# That is pull-based load balancing for free (see the Agent loops tab).

#Failure crosses the boundary too

# An unhandled exception does not kill the process: it is re-raised in
# whoever waits on the ractor, wrapped in Ractor::RemoteError.
boom = Ractor.new { raise "agent crashed" }

begin
  boom.take
rescue Ractor::RemoteError => err
  err.cause.class    # => RuntimeError
  err.cause.message  # => "agent crashed"
end

# Consequence for an agent platform: a worker ractor that dies is GONE.
# Someone has to notice and respawn it -- that is the supervisor's job.

Note what this implies operationally. A ractor that raises is dead, and its incoming queue is orphaned. If your supervisor was blocked in Ractor.select waiting on that worker among others, it now waits forever for a value that will never come. Supervision is not optional decoration on a ractor pool; it is the thing that keeps the pool from silently shrinking to zero.

#Globals, constants, class state

Three categories of "shared thing" behave differently, and all three bite in a Rails-shaped codebase.

# 1. Global variables are main-ractor-only.
$counter = 0
Ractor.new { $counter += 1 }.take
# Ractor::IsolationError: can not access global variables $counter
#                         from non-main Ractors

# 2. Constants are fine -- if what they point at is shareable.
MODEL   = "claude-sonnet-5".freeze          # ok (frozen String)
HEADERS = { "accept" => "application/json" } # NOT ok (mutable Hash)
SAFE_HEADERS = Ractor.make_shareable({ "accept" => "application/json" })

# 3. Class-level mutable state -- the classic Rails memoization idiom -- is out.
class AgentConfig
  def self.settings
    @settings ||= { "model" => "claude-sonnet-5" }
  end
end
Ractor.new { AgentConfig.settings["model"] }.take
# Ractor::IsolationError: can not set instance variables of
#                         classes/modules by non-main Ractors

# The fix is always the same: build it eagerly at boot, deep-freeze it,
# and hand it over as a shareable constant.
class AgentConfig2
  SETTINGS = Ractor.make_shareable({ "model" => "claude-sonnet-5" })
end

The last pattern is the one that will find you. Lazy memoization on a class object (@settings ||= ...) is idiomatic Ruby and is illegal from a non-main ractor, because it mutates an object every ractor can see. Anything you want workers to read must be built and deep-frozen before the first worker exists.

#Ruby 4.0: ports replace the rendezvous

Ruby 4.0 rewrote the messaging API around Ractor::Port. A port is a first-class, shareable queue with exactly one legitimate receiver — the ractor that created it — and any number of senders. Ractor#take and Ractor.yield are gone, replaced by Ractor#value and Ractor#join, which behave like their Thread counterparts.

# Ruby 4.0 (2025-12-25) replaces the take/yield rendezvous with explicit ports.
#
#   REMOVED: Ractor#take, Ractor.yield, #close_incoming, #close_outgoing
#   NEW:     Ractor::Port, Ractor#join, Ractor#value,
#            Ractor.shareable_proc / Ractor.shareable_lambda

port = Ractor::Port.new        # only the CREATING ractor may receive/close

r = Ractor.new(port) do |out|
  out << "progress: turn 1"    # any ractor may push into a port
  out << "progress: turn 2"
  :done                        # still the ractor's return value
end

port.receive   # => "progress: turn 1"
port.receive   # => "progress: turn 2"

r.value        # => :done   (Thread#value-shaped: waits, returns the result)
r.join         # waits for termination, returns the ractor
port.close

# Ractor.select now selects over ractors OR ports, and the old
# yield_value:/move: keyword arguments are gone.

The practical difference for an agent framework is that request/reply stops being a puzzle. In 3.x you either build a rendezvous dance or funnel everything through Ractor.select. With ports, the caller simply ships a reply port along with the arguments.

# Request/reply without a rendezvous: the caller ships a reply port along
# with the arguments. This is the shape every tool call in an agent
# framework wants, and it composes with Ractor.select.

calculator = Ractor.new do
  loop do
    op, a, b, reply = Ractor.receive     # reply is a Ractor::Port
    result =
      case op
      when :add then a + b
      when :mul then a * b
      else raise ArgumentError, "unknown op #{op}"
      end
    reply << result
  end
end

reply = Ractor::Port.new
calculator.send([:mul, 6, 7, reply])
reply.receive     # => 42

# Ports are shareable, so a worker deep inside an agent turn can hold the
# events port and stream progress out without ever meeting the supervisor.

Ruby 4.0 also adds Ractor.shareable_proc and Ractor.shareable_lambda(self:), which directly fix the "Proc's self is not shareable" wall described in tab 03, and Ractor.select now accepts ports as well as ractors, so one select can watch results and streaming events at once.

~/shareability  ·  copy, move, share

The boundary is the design

Every object that crosses between ractors does so in exactly one of three ways, and choosing correctly is most of what "designing for ractors" means. Copy is the safe default and costs time proportional to the object graph. Move is free but destroys the sender's reference. Share is free and permanent, and is only available to objects that are deeply immutable.

# THREE ways an object can cross a ractor boundary.

# 1. COPY (the default). A deep copy of the whole object graph is made;
#    the two sides then have unrelated objects with different identities.
msg = { messages: [{ role: "user", content: String.new("hi") }] }
worker.send(msg)
# inside the worker: received.object_id != msg.object_id

# 2. MOVE. Ownership is transferred with no copying -- the right choice for
#    a big transcript or tool payload you are done with. The sender's
#    reference is invalidated: touching it afterwards raises.
big = "x" * 10_000_000            # ~10MB
mover.send(big, move: true)       # receiver sees 10000000 bytes
big.bytesize
# Ractor::MovedError

# 3. SHARE. Deeply-immutable objects cross by reference, no copy at all --
#    proven by identical object_id on both sides.
FROZEN_CONFIG = Ractor.make_shareable(
  { model: "claude-sonnet-5", max_tokens: 1024, tools: ["search", "code"] }
)
Ractor.new(FROZEN_CONFIG) { |c| c.object_id }.take == FROZEN_CONFIG.object_id
# => true

#War stories

Both of these were hit for real while building the agent-loop prototype in tab 05, and both produce errors that point at the symptom rather than the cause.

# WAR STORY 1 -- the frozen array that wasn't shareable.
#
# This looks completely safe. It is not.
TOOL_NAMES = %w[search calculate].freeze

# `.freeze` froze the ARRAY. The two Strings inside it are still mutable,
# so the array is not *deeply* frozen, so the constant is not shareable:
Ractor.shareable?(TOOL_NAMES)   # => false
#
# Every worker ractor died on its first TOOL_NAMES.include?(...) with
#   Ractor::IsolationError
# and -- much worse -- the supervisor then hung forever in Ractor.select,
# because dead workers never yield and never report.

# Fix A (best): one magic comment at the top of the file.
# frozen_string_literal: true

# Fix B (explicit):
TOOL_NAMES = %w[search calculate].map(&:freeze).freeze

# Fix C (works on any nesting depth):
TOOL_NAMES = Ractor.make_shareable(%w[search calculate])

Why the hang, not just the error

The IsolationError happened inside four worker ractors at once. Each worker died immediately, which meant none of them ever yielded a result, which meant the supervisor's Ractor.select(*workers) blocked forever with no output at all. The visible symptom was a hung script; the actual bug was one missing magic comment. Add # frozen_string_literal: true to every file whose constants cross a ractor boundary, and assert Ractor.shareable? on them at boot so the failure happens at deploy time instead.

# WAR STORY 2 -- tools defined as top-level lambdas.
Ractor.make_shareable(->(x) { x + 1 })
# ArgumentError: Proc's self is not shareable
#
# At the top level `self` is the `main` object, which is a plain mutable
# Object, so no top-level Proc can ever be made shareable.

# Proof that self is the whole problem: build the same lambda somewhere
# whose self IS shareable and it works.
Ractor.make_shareable(Integer.instance_exec { ->(x) { x + 1 } })  # ok

# Fix for Ruby 3.x -- and the better design anyway: tools are module
# functions. Modules are shareable, method bodies are shared code, and
# this is the shape a real tool registry has.
module Tools
  module_function
  def search(args)    = "3 results for #{args["q"].inspect}"
  def calculate(args) = Kernel.format("%g", args["expr"].to_f)
end
Ractor.new { Tools.search({ "q" => "ractors" }) }.take   # ok

# Fix for Ruby 4.0 -- explicit shareable procs with a chosen self:
adder = Ractor.shareable_lambda(self: Integer) { |x| x + 1 }

#A message protocol that survives

For a home-rolled agent framework, the boundary rules translate into one design decision: what exactly is a message? The answer that holds up is "plain shareable data, versioned, with size deciding the transfer mode".

# A message protocol that survives the boundary.
#
# Rule: messages are plain data -- Symbols, Strings, Integers, Floats,
# Arrays and Hashes of the same -- and nothing else. No AR models, no
# Logger, no Proc, no anything holding a socket.

Event = Struct.new(:v, :run_id, :seq, :type, :payload, keyword_init: true)

def emit(bus, run_id, seq, type, payload = {})
  bus.send(Ractor.make_shareable(
    Event.new(v: 1, run_id: run_id, seq: seq, type: type, payload: payload).to_h
  ))
end

# Version every message (`v:`) from day one: worker ractors and the
# publisher are the same deploy today, but they will not be forever.
#
# Small and hot  -> COPY  (events: a few hundred bytes each, thousands/min)
# Large and once -> MOVE  (a finished transcript, a tool's 4MB response)
# Constant       -> SHARE (system prompts, tool registry, model params:
#                          Ractor.make_shareable at boot, never again)

Rules of thumb

  • Prefer copy for anything small and frequent. A few hundred bytes of frozen Hash is nothing next to an LLM round trip, and copy keeps both sides independent.
  • Move when the payload is large and one-way: a finished transcript, a multi-megabyte tool response, a rendered document. The 10MB string in experiment 02 moved with no copy at all, and the sender's reference correctly started raising Ractor::MovedError.
  • Share only what is genuinely constant for the process lifetime, and build all of it during boot so a worker never triggers a lazy initialization.
  • Never put anything holding a socket, a file handle, a Logger, a Thread or an ActiveRecord object into a message. If it cannot be reconstructed from plain data, it does not cross.

~/vs-threads  ·  benchmarks, 4-core Linux container

What ractors actually buy you

The case for ractors rests entirely on one claim: threads cannot use more than one core for Ruby code, and ractors can. The claim is true. What the measurements show is that on Ruby 3.3 and 3.4 the constant factor is so bad that using more cores makes the program slower, and that for the work an agent loop actually does — waiting on a network — threads were never the bottleneck in the first place.

#The GVL, precisely

CRuby holds one Global VM Lock per process. Exactly one native thread may execute Ruby bytecode at any instant, and the scheduler rotates it between threads every few milliseconds. That gives you concurrency: threads make progress in an interleaved fashion, and the illusion is complete for anything that spends its time waiting.

The critical detail is that the GVL is released around blocking operations: socket reads and writes, sleep, file I/O, and C extensions that explicitly declare themselves blocking. While one thread waits on a TCP read, another thread holds the lock and runs. So eight threads each waiting 300ms on an API finish in about 300ms total, not 2.4 seconds — no ractors involved.

What the GVL never gives you is parallelism for computation. Four threads running fib(30) take exactly as long as running it four times in a row; experiment 03 measured threads at 0.98× serial, which is 1.0 plus scheduling noise. Each ractor, by contrast, has its own lock domain, so four ractors can run Ruby bytecode on four cores simultaneously. That is the entire feature.

It is contention, not overhead

Experiment 03b took the slowdown apart hypothesis by hypothesis, and the answer is specific enough to be useful.

0.004s

Spawning and joining an empty ractor takes about 4ms — nowhere near the 1.3s of extra wall-clock time.

0.096s

fib(30) inside a single ractor ran at full speed (0.096s vs 0.099s in the main ractor), and the main ractor stayed at 0.100s afterwards. The VM does not de-optimize permanently.

They really did use 3.6 cores. They just burned 33 seconds of CPU to do 2.7 seconds' worth of serial work — roughly 12× the cycles per iteration once more than one ractor runs at a time.

So the pathology is simultaneity itself: with several ractors executing at once, per-iteration cost explodes, which points squarely at cross-core contention on shared VM-internal structures such as inline caches. A strace during the run showed only 17 futex calls — there is no lock storm at the syscall level, which is consistent with cache-line ping-pong rather than blocking. Setting RUBY_MAX_CPU and RUBY_MN_THREADS changed nothing; do not cargo-cult those environment variables. Ruby 4.0's release notes attribute the fix to reduced global-lock contention and less shared internal data, which matches the measurement exactly.

What to do with this on Ruby ≤ 3.4

Use ractors only for coarse, independent CPU tasks where you control the concurrency level and can absorb the constant factor — or better, do not use them for CPU at all until you are on 4.0. If you need cores today, fork. Real scaling arrives with the 4.0 line, and the code you write for a ractor pool now is the code that gets fast when you upgrade.

#Memory and GC

Ractors share the immutable half of the process: compiled instruction sequences, method definitions, class objects and any deeply frozen constants exist once. Everything mutable is per-ractor, so each one carries its own object heap and its own allocation machinery — substantially more than a thread's couple of hundred kilobytes of stack. Garbage collection is currently a global, stop-the-world event across all ractors, so a heavy allocator in one worker pauses the whole process. Two consequences for sizing: keep pools small and long-lived rather than large and churning, and prefer moving big payloads over copying them, since a copy is a fresh allocation on the receiving heap.

~/agent-loops  ·  the architecture

A supervisor, a job pipe, a worker pool, a bus

An agent loop is a small state machine wrapped around a slow network call: build a messages array, call the model, and if the response contains a tool call, run the tool, append the result, and go around again until the model answers. Your framework owns that loop. The question this tab answers is what shape the loop takes when each concurrent run lives in its own ractor — and the answer, proven by a working prototype, is a four-part topology that fits in about 120 lines.

# The shape of an agent turn, framework-independent:
#
#   messages -> LLM call -> tool_call? -> run tool -> append result -> repeat
#                        \-> final answer -> return
#
# Time budget of one turn in production, roughly:
#   LLM round trip   700ms - 30s   network wait, GVL released
#   tool I/O          10ms - 5s    network wait, GVL released
#   tool CPU           0ms - 2s    parsing, scoring, embedding math  <-- ractors
#   framework glue    <1ms         building the request, appending messages

def run_turn(messages)
  response = llm.complete(messages: messages, tools: TOOL_SCHEMAS)
  return [:final, response] unless response[:tool_call]

  tc     = response[:tool_call]
  result = Tools.public_send(tc[:name], tc[:args])
  [:continue, messages + [response, { role: :tool, name: tc[:name], content: result }]]
end

# Everything marked "network wait" already overlaps perfectly on threads.
# That is why the I/O benchmark shows threads and ractors dead even, and why
# ractors are an answer to the third line only.

#The topology

Why pull, not push

The obvious design is round-robin assignment: the supervisor hands job i to worker i mod N. It is also the wrong one, because agent runs have wildly different durations — one run finishes in two turns, the next spends ninety seconds in a tool. Under push assignment, jobs queued behind a slow agent wait even while three workers sit idle: classic head-of-line blocking. Because Ractor#take is a rendezvous, having every worker call pipe.take in a loop gives you work-stealing semantics for free: the next job goes to whichever worker is ready, and no queue forms behind a straggler.

Ractor references are shareable

This is the detail that makes streaming work. A Ractor object is itself shareable, so the bus can be passed into every worker at spawn time and workers can bus.send(event) from deep inside a turn — mid-tool-call, mid-token — without going back through the supervisor. Funnelling every side effect through one owner is the one sanctioned form of shared access in the ractor model.

#Fitting it to a home-rolled framework

Four rules turn the prototype into something you can run in anger.

1. Agent definitions are boot-time constants

System prompts, tool schemas, model parameters, retry policies — all of it is read-only per process, so build it during initialization and deep-freeze it. Assert shareability at boot rather than discovering it in a worker.

2. Per-run state never leaves the worker

The messages array, the tool scratchpad, token counters: these live inside the worker ractor for the duration of the run. What crosses the boundary is small events on the way out and one result at the end. Copy the events (they are tiny and frequent); move the result if it carries a full transcript.

3. Supervise, restart, resume

A worker that raises is gone and takes its in-flight run with it. The supervisor catches Ractor::RemoteError, logs which agent died and why, spawns a replacement to keep the pool at size, and requeues the run from its persisted transcript.

# Supervision: a worker that raises is gone, and Ractor.select will never
# hear from it again. Catch the RemoteError, respawn, resume from the
# persisted transcript.

def supervise(workers, pipe, bus)
  loop do
    ractor, result = Ractor.select(*workers)
    yield result
  rescue Ractor::RemoteError => err
    dead = err.ractor
    log.error("worker #{dead.name} died: #{err.cause.class}: #{err.cause.message}")
    workers.delete(dead)
    workers << spawn_worker(pipe, bus)      # replace it, keep the pool full
    Runs.requeue_unfinished(dead.name)      # transcripts live in the DB, not the ractor
  end
end

# Two invariants that make this safe:
#   1. every turn is idempotent -- re-running a turn from the persisted
#      transcript must not double-charge a tool or double-post to the UI;
#   2. every run has a turn cap (MAX_TURNS) and a wall-clock deadline, so a
#      confused model cannot pin a worker forever.

4. Sizing

On Ruby 4.0, one worker per core per process is a reasonable starting point, minus whatever the web or job threads need. On 3.3 and 3.4, keep the pool at one or two workers per process and scale by adding processes instead — more concurrent ractors is precisely the condition that triggers the CPU slowdown from tab 04. In both cases the pool is created once at boot and lives for the life of the process; per-task Ractor.new pays 4ms and, on Sidekiq, risks the deadlock in tab 07.

#The bus-owner pattern

Workers emit small frozen event hashes to a bus. One thread in the main ractor drains the bus. One publisher thread — also in the main ractor, where HTTP works, where Rails works, where Timeout works — batches those events and calls Pusher. Nothing in a ractor ever holds an HTTP client.

# The seam, end to end. Two threads in the MAIN ractor:
#   drain thread  -- the only thing that talks to the bus ractor
#   publisher     -- the only thing that talks to Pusher
#
# Worker ractors touch neither. They call bus.send(event) and move on.

bus = Ractor.new do
  loop do
    ev = Ractor.receive
    break if ev == :drain
    Ractor.yield(ev)          # hand each event to the main-ractor drain thread

    event = bus.take          # ONE thread does this. See the Sidekiq tab.

The publisher is where the operational thinking goes. Pusher accepts up to ten events per trigger_batch call, and an agent UI generates bursts — token deltas, tool progress, turn boundaries — that are individually worthless and collectively essential. Batch on a short timer, coalesce aggressively, and treat backpressure as a design case rather than an exception.

# frozen_string_literal: true
# The publisher owns the Pusher client and lives in the MAIN ractor.
# Workers never see it; they only push frozen event hashes at the bus.

class EventPublisher
  BATCH_MAX  = 10      # Pusher accepts up to 10 events per trigger_batch call
  FLUSH_MS   = 80      # coalesce bursty deltas into one HTTP round trip
  QUEUE_MAX  = 10_000  # backpressure ceiling

  TERMINAL = ["agent.completed", "agent.failed"].freeze

  def initialize(client) = (@client = client; @queue = SizedQueue.new(QUEUE_MAX))

  # Called from the bus-drain thread; never from inside a ractor.
  def publish(event)
    @queue.push(event, true)           # non-blocking: raise rather than stall
  rescue ThreadError
    # Queue full. Drop coalescible progress, NEVER drop a terminal event.
    TERMINAL.include?(event[:type]) ? @queue.push(event) : Metrics.increment("events.dropped")
  end

  def run
    @thread = Thread.new do
      batch = []
      deadline = monotonic + (FLUSH_MS / 1000.0)
      loop do
        timeout = [deadline - monotonic, 0].max
        event   = pop_with_timeout(timeout)
        batch << to_pusher(event) if event
        if batch.size >= BATCH_MAX || monotonic >= deadline
          flush(batch)
          batch = []
          deadline = monotonic + (FLUSH_MS / 1000.0)
        end
      end
    end
  end

  private

  def flush(batch)
    return if batch.empty?
    @client.trigger_batch(batch)
  rescue Pusher::Error => err
    Rails.logger.warn("pusher: #{err.class}: #{err.message}")   # never kill the loop
  end

  def to_pusher(event)
    { channel: "private-agent-run-#{event[:run_id]}",
      name:    event[:type],
      data:    event[:payload] }
  end

  def monotonic = Process.clock_gettime(Process::CLOCK_MONOTONIC)
end

Never drop a terminal event

Under backpressure it is entirely reasonable to drop or aggregate message.delta and progress events — the UI will catch up on the next one. It is never reasonable to drop agent.completed or agent.failed: a UI that never hears the run ended spins forever. Terminal events block rather than drop, and are also recorded in the database so the reconnect endpoint can report the truth.

#The pattern that works

# frozen_string_literal: true
# DO THIS INSTEAD. One owner thread per process is the only thread that ever
# touches a Ractor API. Jobs hand work to it and wait on their own Queue.

class RactorPool
  include Singleton

  def initialize
    @inbox   = Queue.new                      # jobs -> owner thread
    @pipe    = Ractor.new { loop { Ractor.yield(Ractor.receive) } }
    @workers = ENV.fetch("RACTOR_POOL", "2").to_i.times.map { spawn_worker(@pipe) }
    @owner   = Thread.new { own }             # exactly one, started at boot
    @owner.abort_on_exception = false
  end

  # Called from any Sidekiq thread. Blocks this job's thread only.
  def compute(payload, timeout: 30)
    reply = Queue.new
    @inbox << [payload, reply]
    result = nil
    Timeout.timeout(timeout) { result = reply.pop }   # a THREAD timeout: legal here
    raise result if result.is_a?(Exception)
    result
  end

  private

  # The owner thread: the sole owner of ractor lifecycle in this process.
  def own
    pending = {}
    loop do
      # 1. accept new work without blocking on the ractors
      while (job = @inbox.pop(true) rescue nil)
        payload, reply = job
        id = SecureRandom.uuid
        pending[id] = reply
        @pipe.send([id, payload])
      end
      # 2. collect whatever finished
      _r, (id, result) = Ractor.select(*@workers)
      pending.delete(id)&.push(result)
    rescue Ractor::RemoteError => err
      @workers.delete(err.ractor)
      @workers << spawn_worker(@pipe)
    end
  end

  def spawn_worker(pipe)
    Ractor.new(pipe) do |queue|
      loop do
        id, payload = queue.take
        [id, Compute.call(payload)]           # plain-Ruby module, no Rails
      rescue => err
        [id, err]
      end
    end
  end
end

class AgentJob
  include Sidekiq::Job

  def perform(run_id)
    run     = Run.find(run_id)                          # Rails: main ractor
    scored  = RactorPool.instance.compute(run.chunks)   # CPU: ractor pool
    run.update!(result: scored)                         # Rails: main ractor
  end
end

Concurrency budgeting

Sidekiq threads and ractor workers compete for the same cores. Size them together: ractor pool size × processes per host should stay at or below the core count, with headroom for the job threads themselves and for GC. Since garbage collection is still stop-the-world across ractors, an over-provisioned pool costs more than it earns. And remember that for the vast majority of agent work — the waiting — Sidekiq's own threads are already the right answer; the pool exists only for the CPU-bound stages.

The operationally honest answer is to run agent workloads in their own processes on their own containers, sized and scaled independently from the web tier.

#The Rails caveat

Rails is not ractor-safe, and will not be soon

Autoloading resolves constants lazily and mutates class-level state, which raises from a non-main ractor. ActiveRecord holds a connection pool, a schema cache and per-class attribute caches, all of them mutable class-level objects. Rails.logger and Rails.cache are globals holding IO and network handles. Experiment 06 showed the primitive version of all of this: can not set instance variables of classes/modules by non-main Ractors.

So the discipline is: a ractor computes over plain data and returns plain data. Load a record in the job thread, hand the worker a frozen hash of what it needs, get a frozen hash back, write it in the job thread. Do every require at boot — on 3.3 it raises inside a ractor, and although 3.4 and later delegate it to the main ractor, a lazy require in a worker is a latency spike and a race you do not need.

One last deployment note: RUBY_MAX_CPU and RUBY_MN_THREADS were measured and made no difference to the Ruby ≤ 3.4 slowdown. They are not a tuning knob for this problem, whatever a blog post tells you.

#Should you use ractors?

#Production checklist

Boot

  • # frozen_string_literal: true in every file whose constants cross a boundary.
  • All configuration, prompts, tool schemas and model parameters built and Ractor.make_shareabled during initialization.
  • Assert Ractor.shareable? on each of those constants at boot, so a bad one fails the deploy rather than a worker.
  • Every require done before the first ractor exists.
  • Ractor pools created once, at boot, sized deliberately — never per task.

Design

  • Tools are modules with module functions, never top-level lambdas or closures.
  • Messages are plain shareable data, versioned with a v: field from day one.
  • Small and frequent payloads copy; large one-way payloads move; constants share.
  • No ActiveRecord, Rails.logger, Rails.cache or HTTP client inside a ractor.
  • All outbound effects funnel through one owner — the bus for events, the main ractor for Pusher.
  • Workers pull from a queue; nothing is assigned round-robin.

Supervision

  • Exactly one owner thread per process touches Ractor APIs. Every other thread waits on a Queue.
  • Ractor::RemoteError is caught, logged with the agent id, and the worker respawned to keep the pool full.
  • Runs are resumable from a persisted transcript, and every turn is idempotent.
  • Hard cap on turns per run, plus a wall-clock deadline checked at every turn boundary.
  • Timeouts come from deadlines and IO#timeout, never Timeout.timeout inside a ractor.
  • Terminal events (agent.completed, agent.failed) are never dropped under backpressure.
# Timeouts: Timeout.timeout spawns a Thread, and Timeout::TIMEOUT_THREAD is
# a global, unshareable Thread -- it cannot work inside a ractor. Use
# deadlines you check yourself, plus real socket timeouts.

MAX_TURNS   = 12
RUN_BUDGET  = 120.0   # seconds of wall clock for a whole run

def run_agent(job, bus)
  deadline = Process.clock_gettime(Process::CLOCK_MONOTONIC) + RUN_BUDGET
  messages = seed_messages(job)

  MAX_TURNS.times do |turn|
    if Process.clock_gettime(Process::CLOCK_MONOTONIC) > deadline
      bus.send({ agent_id: job[:agent_id], type: "agent.failed", reason: "run_budget" })
      return { agent_id: job[:agent_id], error: :timeout }
    end
    # socket-level timeouts are per-IO and ractor-safe:
    #   sock.timeout = 30   (Ruby 3.2+ IO#timeout, raises IO::TimeoutError)

  • Concurrency budget: pool size × processes ≤ cores, with headroom for job threads and GC.

# frozen_string_literal: true
# 07: The Sidekiq/Puma landmine — concurrent Thread -> Ractor waits deadlock.
#
# Sidekiq runs jobs on a pool of threads; Puma serves requests on threads.
# The obvious pattern "each job spawns a ractor and waits for its result"
# WEDGES THE WHOLE PROCESS once several threads do it at the same time
# (and the wedged process ignores SIGTERM — kill -9 territory).
#
# Known upstream: Bug #17826 "Ractor#take hangs if used in multiple Threads",
# Bug #21037 "Ractors hang with multiple threads" — the waiting machinery has
# a literal "TODO: make multithreaded". Reproduced on 3.3.6, 3.4.5 and the
# 4.0 preview (ruby 3.5.0preview1 build).
#
# This file demonstrates it with a watchdog so it exits instead of hanging CI.
Warning[:experimental] = false
STDOUT.sync = true # exit! skips buffer flush; sync or lose all output to a pipe

puts "ruby #{RUBY_VERSION}"

# One thread doing spawn+wait: perfectly fine.
v = Thread.new { Ractor.new { 42 }.take }.value
puts "single thread -> ractor -> take: #{v} (OK)"

# Several threads doing it concurrently: deadlock.
threads = Array.new(3) { |i| Thread.new(i) { |n| Ractor.new(n) { |x| x * 10 }.take } }
deadline = Process.clock_gettime(Process::CLOCK_MONOTONIC) + 8
done = false
until done || Process.clock_gettime(Process::CLOCK_MONOTONIC) > deadline
  done = threads.none?(&:alive?)
  sleep 0.2
end
if done
  puts "3 concurrent threads -> ractors: #{threads.map(&:value).inspect} (fixed in this ruby!)"
else
  alive = threads.count(&:alive?)
  puts "3 concurrent threads -> ractors: DEADLOCK (#{alive}/3 threads still blocked after 8s)"
  puts "=> never block multiple threads on ractor operations; use one owner thread"
  exit! 0 # exit! — regular exit would join the wedged threads and hang too
end
