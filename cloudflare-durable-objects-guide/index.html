Cloudflare Durable Objects

A beginner's guide — from "explain it to a five-year-old" to production patterns.

Durable Objects (DOs) are Cloudflare's answer to a question serverless platforms historically dodged: where does state live? A Durable Object is a tiny server with a globally unique name, its own private database, and a guarantee that only one copy of it exists in the world at any moment. You can have millions of them, they cost nothing while asleep, and Cloudflare handles every part of their lifecycle.

They power real-time chat, multiplayer games, collaborative editors, rate limiters, booking systems, per-user agents — anything where multiple clients need to agree on one piece of state right now.

How this guide is organized

  • 01 — Explain Like I'm Five: the whole idea in a bedtime-story analogy. Genuinely for anyone.
  • 02–07: the engineering track — mental model, a working first object, then the three superpowers (storage, alarms, WebSockets) and the lifecycle rules that make them safe.
  • 08–10: judgment calls — patterns, pitfalls, pricing, and when to reach for KV or D1 instead.
tl;dr A Durable Object = one name → one single-threaded instance → one private, strongly consistent SQLite database, running somewhere close to whoever talked to it first, hibernating for free when idle. Everything else in this guide is a consequence of that sentence.

Prerequisites for the engineering sections

You should be comfortable with JavaScript/TypeScript and have seen a basic Cloudflare Worker before (an export default { fetch } handler). That's it — no distributed-systems background required; the platform's whole pitch is that it deletes most of that homework.

Explain Like I'm Five

No computers in this section. Just clubhouses.

Imagine the whole world is dotted with magical clubhouses. 🏡

Every clubhouse has a name on the door — like "Treehouse #7" or "Emma's Fort." If anyone, anywhere on Earth, sends a letter to "Treehouse #7," it always arrives at the same clubhouse. There is only one Treehouse #7 in the whole world. No copies. No fakes.

Inside each clubhouse lives one caretaker with a big notebook. 📓 When letters arrive, the caretaker reads them one at a time — never two at once — and writes important things down in the notebook. Because there's only one caretaker and one notebook, the notebook never gets scribbled over or mixed up. It's always right.

When nobody has visited for a while, the caretaker takes a nap. 😴 Napping caretakers don't need any snacks (they're free!). But the notebook stays safely on the shelf. The moment a new letter arrives, the caretaker wakes up, checks the notebook, and remembers everything.

And here's the best part: if you need a new clubhouse, you don't have to build one. You just send a letter to a name nobody has used yet — and poof, a clubhouse with that name exists, with a fresh caretaker and an empty notebook. You can make millions of them. ✨

That's a Durable Object:

Keep the caretaker in mind — the engineering sections reuse this picture, because almost every rule about Durable Objects ("don't make one clubhouse do everything," "write things in the notebook before napping") falls out of it.

The Mental Model

From here on, you're a professional engineer. Let's be precise.

A Durable Object is a special kind of Cloudflare Worker that combines compute with co-located state. Formally, the platform gives you the actor model as a managed service. Each object is defined by a JavaScript class; each instance of that class has:

  • A globally unique identity. Derive an ID from a name (getByName("room-42")) or generate a random one. The same ID always routes to the same instance, from any Cloudflare location on Earth. This is what makes a DO a point of coordination: two users on different continents who address "room-42" are talking to the same running object.
  • Single-threaded execution. One instance processes one event at a time. Combined with the runtime's input/output gates (more below), this eliminates the classic read-modify-write race without you writing a single lock.
  • Private, transactional, strongly consistent storage. Each instance owns an embedded SQLite database (up to 10 GB) that lives with the object. Reads and writes are local — microseconds, not network round-trips. No other object or Worker can touch it.
  • A managed lifecycle. Instances are created implicitly on first access, live near where they were first requested, stay warm between requests, hibernate when idle, and can be evicted and revived anywhere without you noticing (storage travels with identity).

The topology

You never talk to a Durable Object directly from the internet. A regular (stateless) Worker fronts it:

Clientbrowser / app, anywhere
→
Workerstateless, runs in every Cloudflare PoP, picks the object by name
→
Durable Objectthe single instance for that name, wherever it lives
⇄
SQLiteprivate storage attached to that instance

The Worker's job is routing and authentication; the object's job is state and coordination. The key design consequence: you scale by having many small objects, not one big one. One object per chat room, per document, per user, per game session, per tenant. Millions of instances are normal and cheap; a single "god object" that everything routes through is the canonical mistake — it serializes your whole app behind one thread (one caretaker can only read letters so fast).

Single-threaded, but not naive: gates

"One event at a time" could be slow and could still be racy around await points. The runtime solves both with two mechanisms you get for free:

  • Input gates: while your code awaits a storage operation, no new event is delivered to the object — so state can't shift under you mid-handler. (Awaiting a fetch() to the outside world does allow other events in; storage awaits are the protected ones.)
  • Output gates: when you write to storage without awaiting, outbound messages (responses, WebSocket sends) are held until the write is confirmed durable. You get write-behind performance with write-ahead safety — a reply can never escape describing state that then fails to persist.
the one-sentence contract Within a single Durable Object, you may write straight-line code that reads state, mutates it, and responds — and treat it as atomic with respect to other requests. The platform makes that safe; your job is just to shard your domain into enough objects.

What DOs are for (and not for)

  • Great fits: real-time collaboration (docs, whiteboards), chat rooms, multiplayer game state, WebSocket fan-out, per-user/per-tenant state and agents, rate limiters and counters, distributed locks/leases, queues and batchers, booking/inventory where correctness matters.
  • Poor fits: static content and caches (use KV), one big relational dataset queried every which way (use D1), blob storage (use R2), fire-and-forget background jobs at scale (use Queues). Tab 10 has a fuller comparison.

Your First Object

A counter you can deploy in five minutes.

Three ingredients: a class extending DurableObject, a Worker that routes to it, and two stanzas of Wrangler config. Scaffold a Worker project first (npm create cloudflare@latest) or drop these into an existing one.

1. The code

src/index.js 
import { DurableObject } from "cloudflare:workers";

export class Counter extends DurableObject {
  // Public methods are callable over RPC from the Worker below.
  async increment(by = 1) {
    // this.ctx.storage is THIS instance's private storage.
    let value = (await this.ctx.storage.get("value")) ?? 0;
    value += by;
    await this.ctx.storage.put("value", value);
    return value;
    // Single-threaded execution + input gates make this read-modify-write
    // safe under any concurrency. No locks, no transactions to write.
  }
}

export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    const name = url.searchParams.get("name") ?? "global";

    // Name -> stub. Same name means same live instance, planet-wide.
    const stub = env.COUNTER.getByName(name);

    // Looks like a method call; is actually an RPC to the object.
    const value = await stub.increment();
    return new Response(`counter "${name}" = ${value}`);
  },
};

Addressing, in full

getByName() is the modern shortcut. The underlying pieces, which you'll see in older code and need for random IDs:

// Equivalent to getByName("demo"):
const id = env.COUNTER.idFromName("demo");   // deterministic hash of the name
const stub = env.COUNTER.get(id);

// Random, unguessable identity — you store the hex string somewhere:
const id2 = env.COUNTER.newUniqueId();
const stub2 = env.COUNTER.get(id2);
const hex = id2.toString();                  // later: idFromString(hex)

Stubs also support stub.fetch(request) — the object handles it in a fetch() method, useful for passing through HTTP or WebSocket upgrades. For plain method calls, RPC (as above) is cleaner and type-safe with TypeScript (DurableObjectNamespace<Counter> in your Env).

gotcha Creating a stub is free and local — it does not contact the object. The instance is created/woken only when you invoke something on the stub. Errors (including "this object is overloaded") surface at call time, not at getByName() time.

Storage API

Every object carries its own SQLite database. Use it like a local variable that happens to be durable.

Storage is reached via this.ctx.storage. On SQLite-backed classes you get three layers over the same database:

LayerCallUse when
SQLctx.storage.sql.exec(query, ...binds)Relational data, queries, aggregates — the main event
Key-valuectx.storage.get/put/delete/listSimple blobs and flags; also what older tutorials show
Alarmsctx.storage.setAlarm/getAlarm/deleteAlarmScheduling — covered in tab 05

SQL

import { DurableObject } from "cloudflare:workers";

export class TodoList extends DurableObject {
  constructor(ctx, env) {
    super(ctx, env);
    this.sql = ctx.storage.sql;
    // Runs on every wake-up (constructor re-runs after hibernation),
    // so schema setup must be idempotent:
    this.sql.exec(`CREATE TABLE IF NOT EXISTS todos (
      id    INTEGER PRIMARY KEY AUTOINCREMENT,
      title TEXT NOT NULL,
      done  INTEGER DEFAULT 0
    )`);
  }

  add(title) {
    this.sql.exec("INSERT INTO todos (title) VALUES (?)", title);
    return this.list();
  }

  complete(id) {
    this.sql.exec("UPDATE todos SET done = 1 WHERE id = ?", id);
  }

  list() {
    return this.sql.exec("SELECT * FROM todos ORDER BY id").toArray();
  }
}

Things worth internalizing:

  • It's synchronous. sql.exec() doesn't return a promise. The database is in the same process — there's no network hop to await. This is the "zero-latency" part of the pitch and it makes code read like single-machine code.
  • Cursors: exec() returns an iterable cursor — .toArray(), .one() (exactly one row or throw), or iterate lazily with for (const row of cursor).
  • Implicit transactions: each exec() is atomic, and the output gate means you rarely need explicit transactions. For multi-statement atomicity use ctx.storage.transactionSync(() => { ... }).
  • Limits: 10 GB per object. Remember the sharding model — that's 10 GB per room / per user / per tenant, not per application.
  • Point-in-time recovery: SQLite-backed objects can rewind storage to any moment in the last 30 days (ctx.storage.getCurrentBookmark() / onNextSessionRestoreBookmark()) — a genuinely underrated safety net.

Key-value

await this.ctx.storage.put("config", { theme: "dark" });   // any structured-clonable value
const config = await this.ctx.storage.get("config");
await this.ctx.storage.put({ a: 1, b: 2 });                // batched write
const map = await this.ctx.storage.list({ prefix: "user:" });
await this.ctx.storage.deleteAll();                        // wipe this object's storage

On SQLite-backed classes the KV API is a thin layer over the same database (there's also a fully synchronous variant at ctx.storage.kv). KV vs SQL is ergonomics, not architecture — start with SQL for anything with structure.

In-memory state vs storage

Instance properties (this.anything) survive between requests while the object stays in memory — a free, always-consistent cache. But hibernation or eviction resets them and re-runs the constructor. The rule:

rule In-memory state is a performance optimization. Anything you'd be sad to lose goes through ctx.storage — the caretaker's notebook, not the caretaker's memory.

To load state exactly once before any request is handled, use ctx.blockConcurrencyWhile() in the constructor — it holds all incoming events until the callback resolves:

constructor(ctx, env) {
  super(ctx, env);
  ctx.blockConcurrencyWhile(async () => {
    this.cache = (await ctx.storage.get("hot-state")) ?? {};
  });
}

Alarms

Every object owns an alarm clock. It's cron, but per-instance and programmable.

An alarm wakes the object at a time you choose — even from hibernation — and runs its alarm() handler. One alarm per object at a time; setting a new one overwrites the old. Delivery is at-least-once with automatic retries (exponential backoff), and the object is guaranteed not to be evicted while an alarm is pending.

import { DurableObject } from "cloudflare:workers";

// A write-batcher: absorb bursts of events, flush at most once per 10s.
export class Batcher extends DurableObject {
  async add(event) {
    // Cheap synchronous-KV write; buffered rows live in this object's SQLite.
    await this.ctx.storage.put(`buf:${crypto.randomUUID()}`, event);

    // Arm the alarm only if one isn't already pending.
    if ((await this.ctx.storage.getAlarm()) === null) {
      await this.ctx.storage.setAlarm(Date.now() + 10_000);
    }
  }

  async alarm() {
    const buffered = await this.ctx.storage.list({ prefix: "buf:" });
    if (buffered.size === 0) return;

    await flushToUpstream([...buffered.values()]);   // your code

    // Only clear after a successful flush — if we throw above, the
    // runtime retries alarm() and nothing is lost.
    await this.ctx.storage.delete([...buffered.keys()]);
  }
}

The patterns alarms unlock

  • Batching/aggregation (above): absorb high-frequency writes in a cheap local buffer, flush downstream on a timer. This is the backbone of many DO-based queues and pipelines.
  • TTLs and cleanup: a session object that deletes its own storage after 24h of inactivity. An object whose storage is empty and has no alarm costs nothing — self-cleaning objects are how you run millions of them guilt-free.
  • Recurring work: re-arm in the handler (setAlarm(Date.now() + interval)) for a per-entity heartbeat — one scheduler per tenant instead of one global cron scanning a table of tenants.
  • Timeouts in coordination: "if the other player hasn't moved in 60s, forfeit" — the game-room object arms an alarm on each turn.
idempotency At-least-once means your alarm() can run twice for one arming (e.g. a retry after a partial failure). Write handlers so a duplicate run is harmless — the delete-after-flush ordering above is the standard shape.

WebSockets

The killer app: one object as the meeting point for many live clients.

Because a name always routes to the same instance, a Durable Object is the natural terminating end for WebSockets that need to see each other: everyone who connects to "room-42" lands in the same object, which can broadcast to all of them from one place. This is how chat, presence, multiplayer cursors, and game state get built here.

Use the Hibernation API

There are two ways to accept a WebSocket. The Web-standard way (server.accept() + addEventListener) pins the object in memory for the life of every connection — you pay duration charges for thousands of idle sockets. The Hibernation API (ctx.acceptWebSocket()) lets the runtime hold the connections while the object itself sleeps; it wakes only when a message actually arrives. Same product, ~zero idle cost. There is no reason to use the old way in new code.

import { DurableObject } from "cloudflare:workers";

export class ChatRoom extends DurableObject {
  // WebSocket upgrades must come through fetch(), not RPC.
  async fetch(request) {
    if (request.headers.get("Upgrade") !== "websocket") {
      return new Response("Expected WebSocket", { status: 426 });
    }

    const [client, server] = Object.values(new WebSocketPair());

    // Hibernation-aware accept: the runtime owns the socket and can
    // evict this object while clients stay connected.
    this.ctx.acceptWebSocket(server);

    // Attach per-connection state that SURVIVES hibernation:
    server.serializeAttachment({ user: crypto.randomUUID(), joined: Date.now() });

    return new Response(null, { status: 101, webSocket: client });
  }

  // Handler methods replace event listeners — the runtime re-creates the
  // object and calls these even after it hibernated.
  async webSocketMessage(ws, message) {
    const { user } = ws.deserializeAttachment();
    for (const peer of this.ctx.getWebSockets()) {
      if (peer !== ws) peer.send(`${user.slice(0, 8)}: ${message}`);
    }
  }

  async webSocketClose(ws, code, reason, wasClean) {
    // On compat dates >= 2026-04-07 the runtime auto-completes the close
    // handshake; on older dates you must call ws.close(code, reason) here.
  }

  async webSocketError(ws, error) {
    console.error("ws error", error);
  }
}

// Worker side: route /room/<name> to that room's object.
export default {
  async fetch(request, env) {
    const name = new URL(request.url).pathname.split("/")[2] ?? "lobby";
    return env.CHAT_ROOM.getByName(name).fetch(request);
  },
};

The hibernation contract

  • While hibernated: clients stay connected to Cloudflare's edge, in-memory state is gone, no duration is billed.
  • On the next message/close/error: the constructor runs again, then the matching webSocket* handler fires. ctx.getWebSockets() returns all live sockets — you don't track them in an array (that array would die on hibernation).
  • Per-connection state goes in serializeAttachment() (survives, up to 2 KB serialized) or keyed rows in storage — not in instance properties.
  • Heartbeats would defeat the whole point (every ping wakes the object), so the runtime can answer them for you: ctx.setWebSocketAutoResponse(new WebSocketRequestResponsePair("ping", "pong")) replies without waking anything.
outbound sockets are different Hibernation applies to sockets the object accepts. An outgoing WebSocket or TCP connection (the object as client) pins it in memory — and bills duration — for up to 15 minutes per connection. Architect so the object is the server whenever possible.

Lifecycle & Memory

What actually happens between "getByName" and "hibernated."

Stub createdlocal, free, nothing happens yet
→

→
Activeprocessing events, one at a time
→
Idle in memory~seconds; warm, unbilled if hibernatable
→
Hibernated / evictedmemory gone, storage + identity + sockets remain

Details engineers actually need:

  • Placement: the instance is created in a Cloudflare data center near the first caller and generally stays in that region; other callers reach it over Cloudflare's backbone. For latency-sensitive global apps, shard by geography where it makes sense (e.g. getByName("eu:" + roomId) from EU users) rather than fighting placement.
  • The constructor runs on every wake-up — first creation, post-hibernation, post-eviction, and after every code deploy (deploys restart all instances). Keep it fast and idempotent; heavy async init goes in blockConcurrencyWhile().
  • Eviction triggers: idleness, deploys, runtime maintenance, or exceeding memory (128 MB, same as Workers). You cannot prevent it; you can only be correct in the face of it. That's why the rule from tab 04 exists: durable facts live in storage.
  • What keeps an object awake (and billing): in-flight requests, non-hibernatable WebSockets, outbound TCP/WebSocket connections (up to 15 min each), and code that holds the event loop. What does not: hibernatable sockets, pending alarms (the alarm guarantees a future wake-up but doesn't keep it in memory).
  • "Deleting" an object = ctx.storage.deleteAll() + deleteAlarm() + letting it go idle. Identity is virtual; an object with no storage, no alarm, and no traffic costs nothing and is indistinguishable from one that never existed.
  • Errors and overload: if an object is overloaded or its host is restarting, calls on the stub throw (some with a .retryable hint). Treat a DO call like any RPC: timeouts and retry policy live in the calling Worker.
mental checksum Identity and storage are permanent; the process is disposable. If your object behaves correctly when killed between any two events and revived cold, you've designed it right.

Patterns & Pitfalls

The judgment layer: what separates a demo from a system.

Patterns that recur everywhere

  • One object per unit of contention. Room, document, user, tenant, SKU, device. The name is the shard key. If you can name the thing users fight over, you can usually ship the feature as "that name's object arbitrates."
  • Rate limiter: getByName(clientIP), token bucket in storage (or even in memory, if approximate-after-eviction is acceptable). Strongly consistent by construction — no Redis, no race.
  • Distributed lock / leader election: the object is the lock; whoever's request gets processed first holds it. Lease expiry via alarm.
  • Fan-in, then fan-out: ingest bursty events (fan-in via cheap local writes), batch via alarm, push downstream; or accept one authoritative update and broadcast to N hibernating WebSockets (fan-out).
  • Registry + workers: a directory object holding the list of per-entity objects (created with newUniqueId()), each doing its own work. Keep the directory's job tiny — it's the one object that everything touches.
  • Agent per user/session: LLM agents need exactly what DOs sell — serial execution, durable memory, timers, and a WebSocket to the client. (Cloudflare's Agents SDK is a framework on top of Durable Objects.)

Pitfalls, ranked by how often they bite

  1. The singleton bottleneck. One object for "all users" caps your app at one thread's throughput (roughly, low thousands of simple requests/sec — far less if handlers do real work). If an object's name would be a constant string, ask hard whether the design is right. Where a global view is truly needed, shard N ways and aggregate.
  2. Treating memory as durable. Works in dev (nothing hibernates while you're poking it), loses data in prod. Constructor + storage, always.
  3. Forgetting the migration stanza. Binding without new_sqlite_classes → deploy-time error. Migrations are append-only with unique tags; renames/deletes get their own entries.
  4. Standard WebSocket API in production. Duration billing for every idle connected second, times every client. Use hibernation (tab 06); the API difference is minutes of work.
  5. Chatty cross-object calls. Object A awaiting object B on every request reintroduces network latency you just designed out, and risks call-graph cycles (A→B→A deadlocks on A's own single thread). Prefer telling (fire-and-forget updates, batched syncs) over asking.
  6. Doing slow upstream work while holding the room. A 2-second fetch() to a third-party API inside a hot object's handler stalls every other caller of that object (events queue behind it). Push slow I/O to the calling Worker, a Queue, or an alarm-driven batch.
  7. Unbounded per-object growth. 10 GB is the ceiling per object; if one tenant's object can grow forever, shard by time or sub-key before it matters, and let old objects self-delete via alarms.
  8. Auth inside the object only. The fronting Worker should authenticate before routing — every request that reaches an object bills a request and can wake it. Don't let anonymous traffic wake a million caretakers.
testing note wrangler dev runs DOs locally with real storage semantics, and @cloudflare/vitest-pool-workers lets unit tests construct objects directly and inspect their storage. Concurrency bugs are rare by design here — most test effort goes to alarm idempotency and hibernation-revival paths.

Pricing & Limits

Numbers as of August 2026 — always confirm against the pricing page.

Durable Objects are available on the free plan (SQLite-backed classes only). Two meters: compute (requests + duration) and storage (SQLite rows/GB — billing live since January 2026).

  • Free-plan limits reset at 00:00 UTC; exceeding one makes that operation type fail with errors for the rest of the day (plan for this in clients).
  • Duration is the meter that punishes bad architecture. Hibernatable-idle objects bill nothing; a non-hibernatable WebSocket or an outbound connection bills wall-clock. 1 GB-s = 8 object-seconds at 128 MB, so 400k GB-s ≈ 3.2 million object-seconds a month included.
  • Each RPC session bills as one request; chained calls on a returned RpcTarget stub share the session. Incoming WebSocket messages bill in 20:1 batches (20 messages : 1 request-unit); outgoing are free.

Storage (SQLite backend)

Billed like D1: rows read, rows written, and GB-month of stored data, each with monthly included allowances on the paid plan (e.g. billions of rows read and 5 GB-month included; overage on the order of $0.001/million rows read and ~$0.20/GB-month). Free plan gets daily row allowances and 5 GB total. KV-API calls map to row operations under the hood. The exact rates move occasionally — check the pricing page before capacity-planning.

Quick decision guide

  • "Two clients must agree, immediately" (seat booking, game move, doc edit, rate limit) → Durable Object. This is the only option on the list that gives you serialized, strongly consistent read-modify-write.
  • "Read-heavy, written rarely, staleness fine" → KV. Don't burn a DO on feature flags.
  • "I want to query across all my entities" (reports, admin dashboards, joins over all users) → D1. Per-entity DO storage is invisible to global queries — a common hybrid is DOs for live state that asynchronously sync summaries into D1 for analytics.
  • "It's a file" → R2.
  • "Background jobs, retries, decoupling producers from consumers" → Queues; "multi-step processes with sleeps and retries" → Workflows (itself built on DOs, which tells you something).
the litmus test Ask: "does this data have a natural owner with a name, and do writers contend for it?" Yes → Durable Object. No owner / no contention → KV, D1, or R2 by shape.
